## 0. 论文的目标（先把这个定死）

项目目标不是「找出哪些 harness 技巧能提分」，而是仓库文档反复写明的这一条：

> **把 Recursive Language Models（RLM）的三个核心能力扩展到结构化数据库推理，
> 并在导师设定的约束下检验它们：generator 固定为 `gpt-5.4-mini`、无 fine-tune 通道，
> 只能动执行环境、工具、验证器与预计算知识——「一个小模型配上正确的 harness 能走多远」。**
> —— [docs/experiment-plan/README.md](../experiment-plan/README.md) §0.1/§1、[README.md](../../README.md)

三个能力及其可测化（计划 §1.1–1.3）：

| 能力 | 内容 | 对应实验族 |
|---|---|---|
| **一：可编程上下文与代码化推理** | Schema/metadata/patterns/QueryPlan/observation 组织成可检索可组合的结构，而非一段不可追踪的长 Prompt；`search` / `slice` / `compose` | **C（E3）内容与交付** + **E（E5）主动访问** |
| **二：受控执行环境** | 工具、DB 访问、observation、终止原因、上下文读取全部由 manifest + capability gate 约束，运行故障与语义错误分离 | **B（E2）**，及 E0 已含的执行环境本身 |
| **三：可验证的自我改进与分而治之** | Root 形成全局 QueryPlan 并按执行反馈修正；仅在存在可独立验证的复杂 SubPlan 时用受控 depth-1 Leaf，且必须与**等预算的额外 Root 思考**对照 | **D（E4）** + **F（E6）** |

### 0.1 一个必须先讲清的边界：每个能力都有两半

计划 §7 自己划了这条线：

> 「E3 研究 **Offline 中有什么内容，以及固定策略选出的内容是否有价值**；
> E5 研究 **模型能否通过程序化接口主动搜索、切片和组合同一批内容**。
> E3-C 的确定性词法选择和 FK 邻接在模型调用前完成，**不算模型主动 context exploration**。」

**这条线是全文的骨架。** 每个能力都可以由两个主体来行使：

| | 由 harness 确定性行使 | 由模型自主行使 |
|---|---|---|
| 能力一 | E3-C 按题确定性检索片段 → **有效 +4.82 pp** | E5 模型主动 `search/slice/compose` → **无效** |
| 能力二 | 执行环境 + capability gate + manifest → **有效**（+9.0 的来源；使归因成为可能） | —（该能力本身不要求模型判断） |
| 能力三 | E6 harness 确定性触发的改写 → **+1，零打坏，两次一致** | E4-A 模型自定 QueryPlan → **−6**；E6-B 模型消化反馈 → **与纯重试不可区分** |

论文的答案因此**不是**「三个能力都不兑现」，而是：

> **三个能力各自被劈成两半——由 harness 确定性完成的那一半有效，
> 要求模型自主判断何时、如何行使的那一半无效。**

沿途为做这件事而建立的 error tracking 基础设施，产出了三条独立于原目标的结论；
它们必须挂在这条分界线下面讲，不能反客为主。

## 1. 论文主张与贡献

### 1.1 一句话主张

> 在冻结的商用小模型上，RLM 三能力的成败不按「能力」切分，而按**谁来行使**切分。
> **凡是由 harness 确定性完成的都有效**：把 schema 组织成按题交付的片段（+4.82 pp，
> 六个受测机制中唯一被接受的）、受控可审计的执行环境（+9.0 的来源，且使单变量归因成为可能）、
> 对最终 SQL 的确定性改写（+5 题，而同一批约定写进 Prompt 为 0）。
> **凡是要求模型自己判断何时、如何行使的都无效**：主动的 `search/slice/compose`
> （所针对的约束不存在，利用率约 4%）、自我验证（6 次独立设计全部净负）、
> 分而治之（委派未创造新信息，五轮迭代净收益恒为 0）。
> 广为引用的「承诺前有效 / 承诺后无效」时序律，是这条分界线在时间维上的一个特例。
> 最后，该基准上的可测 headroom 必须用**外部独立修正版 gold** 才能诚实估计——
> 用自己写的修正答案会得到反向的错误结论。

### 1.2 五条贡献

| # | 贡献 | 性质 | 最强证据 |
|---|---|---|---|
| **C1** | **分界线：确定性交付 vs 模型自主行使**（论文主干，回应原目标）——三能力各自被劈成两半，一半有效一半无效 | 混合结果，主贡献 | E3-C +4.82pp vs E5 +109% token/准确率持平；后处理确定性改写 +5 vs 同一批约定写进 Prompt 违反计数 24 vs 25；E6 确定性改写 +1/零打坏 vs E6-B 与纯重试不可区分 |
| **C2** | **时序律**（C1 的时间维特例）：承诺前落地取证有效（+9.0），承诺后复核 6 次全部净负 | 结构性负面结论 | 失败题 wrong→correct 恢复**三次运行精确为 0**；91.1% 的失败在第一版草稿即定型 |
| **C3** | **「改形状可以，改语义不行」判据**：确定性后处理的合法边界 | 新判据（可迁移） | 三条规则在外部修正 gold 上 −16 / +8 / −2，判据事前即可预测；iter15 独立复现 +18 |
| **C4** | **基准质量结论 + 一次自我否证**：163 道失败全量定责，gold : 模型 ≈ 2 : 1；但「标注噪声压低了我们的分数」**不成立**（净额 −1） | 基准学 + 方法论 | 外部修正版 gold 重评 67.07% vs 原始 67.27%；判别力梯度 84% / 25% / 12% |
| **C5** | **错误驱动的单变量消融方法与 provenance 基础设施** | 方法论 | 预注册接受条件、manifest+SHA-256、capability gate、双标签分类；**分类器修复一次就反转了 E4-A 的归因** |

### 1.3 明确不主张的

- 不主张刷新 BIRD SOTA
- 不主张「ReAct 无用」——它是最大单项增益之一（+9.0），C2 的全部意义在于区分时序
- **不主张「三个能力都无效」**——能力一的内容侧是全项目唯一被接受的模型侧机制，
  能力二按项目定义即为「有效但不作为准确率机制」。**v0.2 大纲在这里是错的**，见修订记录
- 不主张「模型真实水平更高」——§16 台账里这是被外部数据明确否证的一条
- 不主张 RLM 本身无效——只主张**要求模型自主行使**的那一半在本任务这一规模上前提不成立

## 第一部分：设定

### 1. Introduction（1.5 页）

- 1.1 **目标**：RLM 的三个能力能否扩展到结构化数据库推理。为什么 Text-to-SQL 是合适的检验场——
  它同时需要长上下文组织（schema/metadata）、可执行验证（真库）和多阶段分解（嵌套聚合），
  正是 RLM 三能力各自声称要解决的问题
- 1.2 **约束**：模型冻结（`azure/seminar-gpt-5.4-mini`，`reasoning_effort=high`），无 fine-tune 通道。
  这不是资源限制而是研究问题本身——「小模型 + 正确 harness 能走多远」
- 1.3 **为什么必须做消融而不是堆模块**（计划 §0.1）：E0 的 259 条失败来自不同层面，
  三个能力不能作为一个整体实验；由此确立「运行 → 轨迹分析 → 错误迁移 → 更新假设 → 下一实验」闭环
- 1.4 三个原始直觉与它们的下场（预告全文）：

  | 直觉 | 下场 | 出处 |
  |---|---|---|
  | 把 schema 组织成按需交付的片段会更准 | **成立，+4.82 pp**——全项目唯一被接受的模型侧机制 | §7 |
  | 受控可审计的执行环境值得建 | **成立**，且它是 +9.0 的来源；但收益不在准确率轴上 | §5.1 / §6 |
  | 再进一步，让**模型自己**主动取用上下文会更准 | 不成立：利用率约 4%，外部化是净负担 | §9 |
  | 让模型多验证一步会更准 | 不成立：6 次独立设计全部净负 | §12 |
  | 递归分解能处理复杂查询 | 不成立：五轮迭代，委派题净收益恒为 0 | §10 |
  | 剩下的失败是模型能力不足 | 不成立：163 道全量定责后纯模型推理错误仅 11.7% | §15 |

  **前两条成立、中间三条不成立，差别不在能力，在谁来行使**——这就是 §11 的分界线。

- 1.5 贡献列表（§1.2）+ 路线图 + **图 1** 实验时间线

## 第二部分：三个能力的检验

### 5. 阶段 A：基线与控制流（2.5 页）

**主张**：早期增益来自「让模型看到真实数据」和「让模型多想」；随后为了让归因成立，
不得不放弃一个更高的分数去重建一个来源可审计的基线。

- 5.1 **legacy 基线弧**（全 500 题，官方口径）：

  | 配置 | 准确率 | 结论 |
  |---|---:|---|
  | Baseline 1 单轮 schema→SQL | 55.20% | 对比基准 |
  | Baseline 2 + 关键词表过滤 | 51.60% | **朴素剪枝有害**（丢表且无回退） |
  | DB-RLM harness v4（ReAct + 活库工具） | 64.20% | **+9.0**，最大单项增益之一 |
  | + `reasoning_effort=high`，train few-shot k=1 | 69.20% | **+5**，能力是瓶颈不是指令 |
  | 同上，无 few-shot | 68.60% | 检索非承重 |
  | 3-run 结果投票 / 5-run 最优 | 71.10% / 72.30% | 后者含 2 个 dev-pool 检索运行（已披露，可比性最差） |

  > ⚠️ 仓库里只有 `baselines/run_bird_b1_azure.py` 与 `run_bird_b2_azure.py` 两个**命名**基线。
  > 若你说的「baseline 3」指 DB-RLM harness v4，本节即已覆盖；见 §7 决策问题 1。

- 5.2 Ensemble 定律：投票需要强度相近、犯不同错的投票者；1 强 + N 弱 < 强者单独（67.8 < 70.2）
- 5.3 **泄漏事件（2026-07-04）**：legacy in-domain retriever 的池子是「答对的 dev 题 + 其 gold SQL」，
  相似检索会返回题目自身，约 73% 的池内题命中自己的 gold。**全部 pre-fix 数字撤回**；
  修复后审计 0/100 self-hit；此后 eval set 完全不碰。
  **这是本项目 provenance 基础设施的直接起因，必须写**
- 5.4 **clean 重建（2026-07-13）**：拆开 prompt/knowledge/config/state/capability；
  `clean-protocol-v1` 只含工具与提交协议，剥离所有可能来自 eval 分析的 SQL 规则；
  legacy `db_hints` 隔离到 `legacy-e0`。
  代价可量化：dev500 上 `clean-e0` **61.40%** vs `legacy-e0` **67.80%**——
  **那 6.40 pp 就是被剥离的 eval 调优**
- 5.5 **E0**：core197 上 35.03% / 33.50%（均值 34.26%），62 稳定对 / 124 稳定错 / 11 不稳定；
  259 条失败 → 机制优先级表（决定了 E2/E3/E4/E5/E6 的顺序）
- 5.6 **E1 strict verified-final（拒绝）**：前 70 题配对 40.00% vs E0 均值 42.14%；
  调用 2.03×、token 2.00×、延迟 1.75×；103 次 `final.blocked` 覆盖 63/70；
  **稳定失败恢复 0、稳定正确退化 3**。`UNVERIFIED_FINAL` 归零证明形式约束生效，
  但形式可验证性 ≠ 语义正确——**这是时序律的第一次出现，此处埋线**

### 6. 阶段 B：基础设施与能力隔离（E2）→ 能力二**有效，但不是准确率机制**（0.75 页）

**主张**：能力二**成立，但它的收益不在准确率这条轴上**。计划原文即写明它不作为准确率机制
（[计划 §0](../experiment-plan/README.md) 大类 B）。它交付两样东西：
执行环境本身是 legacy 弧上 **+9.0** 的来源（§5.1），而 gate + manifest 交付的是**可归因性**——
后者的价值在本项目中被一次事故直接证明。
**不要把这一条写成负面结论**（v0.2 大纲的错误）。

- 6.1 E2-A 结构化 observation 前置条件（`{sql,status,columns,rows,error,truncated}`、
  独立终止原因、断点续跑、usage 缺失单列）——**通过才允许跑正式实验**
- 6.2 **E2-B capability gate**（历史结果名 `E4-R0`）：前 50 题 19/50 = 38%，E0 为 38%/40%；
  **110 个工具事件全部在允许集合，0 越权**。接受为基础设施，**不作为准确率机制**
- 6.3 **能力二价值的直接证据 —— 分类器修复（2026-08-07）**：原分类器只查关键字是否出现，
  不比较 GROUP BY/ORDER BY 的实际列、JOIN 键、LIMIT 值。修复后重跑全部 7–8 个已完成实验的分类：
  **Schema/Join 从最小类（38, 14.67%）变最大类（97, 37.45%）**，过滤类 67→36。
  **这直接反转了 E4-A 的拒绝归因**（结论不变，解释此前是错的）。
  没有结构化 trace 与可重放的分类流水线，这次修正不可能发生

### 7. 阶段 C：Offline Knowledge（E3）→ 能力一·**确定性交付侧，有效**（3.0 页）

**主张**：**能力一的内容与交付侧成立**——这是全项目唯一被接受的模型侧机制。
但它成立有一个前提：**所供信息必须是模型不可自行获得的**；
且交付方式是 **harness 在模型调用前确定性地选好**，不是让模型自己去找（后者是 §9）。

- 7.1 Offline 系统的完整定义（计划 §7）：内容构建层 / artifact 管理层 / 运行时交付层；
  **artifact 完整 ≠ 全部塞进 Prompt**
- 7.2 六个子实验：

  | 实验 | 干预 | core197 | 判定 |
  |---|---|---:|---|
  | E3-A | train-only 静态 patterns 全局注入 | 37.06%（+2.79pp） | 弱证据，不作父配置 |
  | E3-B | patterns 替代 few-shot（移除信息） | 36.55%，token **+4.54%** | 拒绝（准确率降且成本未降） |
  | **E3-C** | **Offline Schema Context 替代 runtime full Schema** | **39.09%（+4.82pp）** | **接受**，成为 E4-A 父配置 |
  | E3-D | Query Mining（问题 n-gram → SQL 结构） | 28 slot **0 个**过跨库门禁 | 不可行 |
  | E3-E | 从通过的 E3-D 移除 few-shot | **未运行**（条件实验） | 前置未通过 |
  | E3-F | 完整 Offline 系统集成 | v1/v3 在 53/197 中断（21/53） | 冻结为历史诊断；新版被门禁安全阻断 |

- 7.3 **E3-C 机制细节**：全量 schema 注入 → 按题**确定性检索**的相关片段（表/字段描述、PK/FK 图、
  join 的 cardinality 与 fan-out、值格式），未选中表只给 names-only 索引。
  dev500 复核 **+3.20 pp**；表召回 **492/500 = 98.4%**，且**漏表的 8 题准确率 87.5% 反而更高**
  （漏表 ≠ 不可见，names-only 索引仍在）。代价 token/题 **+14.29%**——
  只能称「准确率有效」，不是「效率改进」
- 7.4 **E3-C 成功 vs E3-D 失败的分界（本章的真正结论）**：
  E3-D 最佳 slot `output_count` 精度 0.906，而**模型自身在同一判断上是 0.891**——只强 1.5 pp，
  折算期望收益约 +0.6 pp（197 题约 1 道），**低于实测 Prompt 扰动噪声**。
  → **重复模型已有能力的信息不产生收益，无论统计验证多严格。门禁拒绝它是对的**
- 7.5 E3-F v1/v3 的诊断价值：Schema v3 在 53/53 题都交付全库表——**零 miss 是全表注入造成的，
  不是检索精度证据**；Query Mining v1 平均 2.85 张卡/题，仅 16/53 命中 gold shape。
  说明「小幅准确率变化 + 显著成本增加」的组合应当直接怀疑机制退化成了注入
- 7.6 **train 审计过的提示词规则（+2.80 pp）**：legacy 提示词值 +6.40 pp 但标注
  `legacy-eval-tuned-unaudited`；逐条拿 train 验证后**采纳 2 条、剔除 2 条**

  | 规则 | train 支持度 | 采纳 |
  |---|---:|:--:|
  | 最值用 `ORDER BY...LIMIT` | 90.3%（n=1542） | ✅ |
  | 单问句只投影一列 | 84.5%（n=8693） | ✅ |
  | 是非题返回 YES/NO 字面量 | 41.0%（n=39） | ❌ train 反对 |
  | 多问句投影多列 | 28.6%（n=595） | ❌ train 反对 |

  机制验证（**不经过评分**）：最值写错 **19 → 4**，单问句多投影 **81 → 70**。
  泛化性：train 69 库与 dev 11 库**完全不相交**，迁移差 +1.7% / −2.4%，dev 逐库 8/8、11/11 多数遵守。
  **边界**：只证明 BIRD 内部跨库泛化，跨数据集很可能不成立

### 8. 阶段 D：在线题目级形式化（E4-A）→ 能力三·前置（1.0 页）

**主张**：能力三要求 Root 先形成可检查的全局 QueryPlan。该前置本身被拒绝。

- 8.1 机制：同一次 Root 响应内输出结构化 QueryPlan + Output Contract（不增加独立 Planner call），
  含 `target_entity` / `grain` / `filters[].scope` / `answer_type` / `expected_result_shape` 等
- 8.2 结果：**71/197 = 36.04%**，较父配置 E3-C **−6 题**；恢复 3、回退 9；token/题 +6.67%；
  新增 4 个 missing FINAL。**预注册接受条件未通过 → 拒绝**
- 8.3 **归因反转（2026-08-07）**：原报告「聚合/排序改善 −4、Schema 轻微恶化」；
  修复后分类器重算为**聚合/排序 +4（自己的目标类别变差）、Schema/Join −4（改善）**，
  目标类 recovered:regressed 由 3:3 变 **3:5**。拒绝结论不变，解释此前是反的
- 8.4 轨迹证据：**82/126 是「计划被忠实执行但计划本身错了」**；19 个使用合法 revision 的题只有 2 个正确，
  wrong→correct 恢复为 0 → **瓶颈是错误的计划，不是 SQL 没遵守计划**（直通 §12）

### 9. 阶段 E：RLM 上下文环境（E5）→ 能力一·**模型自主访问侧，无效**（1.0 页）

**主张**：**能力一针对的约束在本任务不存在。**

- 9.1 **E5-A 通过**：把 `hint`/`few_shot`/`offline_metadata` 移入只读 context store。
  信息等价 **197/197 逐字节一致**、可达性 11 题 **59 次主动读取（5.36 次/题，0 题未读）**、
  事件日志仅含 `context.list`/`context.read`/`db.execute`，**无越权**。
  **能力实现是对的，结论仍是负的**
- 9.2 **成本是决定性的**：+108.9% total token、+312.3% 延迟、+100% LLM 调用，准确率持平（5/11）；
  prompt token 降 17.5% 但推理 token 涨 283%（多轮读取各携带完整隐藏推理 + 大量重复读取）
- 9.3 **根因是结构性的**：知识载荷仅 **726–2,572 tokens**，prompt 约 5,171 tokens，
  **上下文利用率约 4%**。context store 针对「上下文装不下」的约束，该约束在此不存在——
  **把 store 做得更快也无法创造本来不存在的收益**
- 9.4 **一个被推翻的预测（值得写）**：基于 ReAct 循环测量曾预期「模型懒得读」，实测相反——
  模型为**获取信息**调用 5.36 次，却只为**验证 SQL** 调用 1.6 次，且 store 模式下 `sample_values` 降至 0。
  **印证：验证行为不是工具可达性问题**
- 9.5 **E5-B 不建议作为准确率实验运行**：两条接受轴先验都差——89–93% 的残留失败所需信息
  本已在上下文中（查找不是瓶颈），而 E5-B 会进一步增加调用轮次

### 10. 阶段 F：受控递归（E6）→ 能力三（1.75 页）

**主张**：**分而治之的前提不成立，且委派本身未创造新信息。**

- 10.1 递归的三个常见价值主张，两个已被本项目自身数据否定：

  | 价值主张 | 本项目证据 | 状态 |
  |---|---|---|
  | 上下文管理（每个 leaf 看得更少） | 利用率约 4%，外部化是净负担（§9） | 已否定 |
  | 子结果验证 | 验证类机制全败，恢复率恒为 0（§12） | 已否定 |
  | 更多计算 | — | E6-A 等预算对照 |
  | 结构约束 / 错误隔离 | — | E6-B |

- 10.2 **触发设计一：粒度不变量 —— 未通过定容**。命中 4 题 / 误报 2 题（精度 66.7%），
  靶子低于 6 题方差。**更根本的是前提被证伪**：统计「聚合建立在会扇出的 JOIN 行集上」，
  只有 pred 有 21 / **只有 gold 有 18** / 两边都有 29 ——
  **BIRD 的 gold 自身在近半数稳定失败中按扇出粒度聚合，扇出不是错误信号**
- 10.3 **触发设计二：空集 —— 通过定容，进入 E6-A/E6-B 等预算对照**（各重复 3 次）：

  | 处理 | 错题转正 | 对题打坏 | 净 |
  |---|---|---|---:|
  | 确定性改写（空集时解除守卫） | **1** | **0** | **+1** |
  | Arm A 等预算，无事实 | 1/25 = 4.0% | 1/3 | 0 |
  | Arm B 等预算 + 机械定位事实 | 1/23 = 4.3% | 2/3 | −1 |

  参考基线（纯重跑）：错→对 1.7%、对→错 10.4%。
  **两臂统计上无法区分**，各自唯一一次转正都只出现在 1/3 重复中且是不同的题。
  **即使反馈是确定性机械测量、绝对可靠，相对纯重试仍无增益**
- 10.4 **五轮迭代的递归实现（dev200/dev500 系列运行）**：

  | 版本 | 改动 | leaf 查库率 | 委派题净收益 |
  |---|---|---:|---:|
  | v1 | 纯文本 leaf | — | 0 |
  | v2 | leaf 可查库 | 0% | 0 |
  | v3 | 强制查库 | 0% | −2 |
  | v4 | 给 leaf schema | 23% | 0 |
  | v5 | 给确切可照抄的代码块 | **94%** | **0** |

  v5 中 leaf 确实查库并答对（返回真实查询结果），**机制端到端跑通，净收益仍为 0**。
  **结构性原因：parent 自身即有 `db.execute`，leaf 查到的 parent 本就查得到——委派未创造新信息**
- 10.5 **一个必须坦白的发现**：项目此前所有「RLM 能力」实验测的都不是递归本身——
  递归原语一直在 REPL 里，但**没有任何提示词提到过它**，实测 **0/197 次调用**
- 10.6 **否定的边界**：本轮测的是「反馈即文本」形式。**「强制结构约束」形式
  （中间结果必须实际执行且不可绕过）从未被测试**，因为其确定性触发在 197 子集上没有靶子。
  公平检验它的前置条件是**构建能力失败密度更高的评测集**

### 11. 三个能力的合并结论：分界线在能力内部（1.0 页）

**本章是论文的转折点，也是 C1 的正式陈述。**

- 11.1 **不是三个能力各得一个结论，而是每个能力得到两个**：

| 能力 | 由 **harness 确定性**行使 | 由**模型自主**行使 |
|---|---|---|
| **一** 可编程上下文 | **E3-C 有效**：按题确定性检索片段替代全量 Schema 注入，core197 **+4.82 pp**、dev500 **+3.20 pp**，表召回 98.4%。**六个受测机制中唯一被接受的** | **E5 无效**：信息等价 197/197、可达 11/11、0 越权——机制实现完全正确，但 +108.9% token、+312.3% 延迟、准确率持平。**所针对的约束不存在**（利用率约 4%） |
| **二** 受控执行环境 | **有效，但不在准确率轴上**：执行环境本身是 **+9.0** 的来源，30s abort 与 API 重试（+2.4）是可靠性增益；gate + manifest 交付**可归因性**（E2-B：110 事件 0 越权、准确率持平） | —— 该能力**本身就不要求模型判断**，因此没有「自主」的一半。这正是它没有失败的原因 |
| **三** 自我改进与分而治之 | **有效但靶子极小**：E6 空集触发的确定性改写 **+1、零打坏、两次独立运行一致** | **无效**：E4-A 模型自定 QueryPlan **−6**，且**自己的目标类别变差**；E6-B 模型消化确定性反馈，与纯重试**统计上无法区分**（4.3% vs 4.0%） |

- 11.2 **分界线的三次跨栏对照**（同一批内容、只换行使主体，因此是受控的）：

  | 内容 | 由 harness 确定性行使 | 由模型自主行使 |
  |---|---:|---:|
  | 三条书写约定 | **+5 题**（两次独立测量一致） | **0**（违反计数 24 vs 25） |
  | 空集后的补救 | **+1**，零打坏 | 与纯重试不可区分，且打坏率 33–67% |
  | 同一批 schema/hint/few-shot | E3-C **+4.82 pp** | E5 准确率持平、成本翻倍 |

  **三对对照方向完全一致。** 这不是三个孤立结果，是同一条规律的三次独立显现

- 11.3 **因此原目标的答案要这样写**：RLM 的三个能力**作为能力都是真实的**——
  信息可以被组织成按需交付的片段（有效）、执行环境可以被受控与审计（有效）、
  分解可以被确定性地触发（有效但靶子小）。
  **不成立的是 RLM 隐含的那个前提：模型能自主判断何时、如何行使这些能力。**
  在冻结的商用小模型上，这个前提三次落空
- 11.4 **这条分界线的可迁移形式**：`harness 确定性完成 > 模型自主判断`——
  §12 的时序律是它的时间维特例，§14 的「改形状/改语义」判据是它的**边界条件**
  （确定性也不是无条件安全，见 `count_no_distinct` 的 −16）

### 12. 时序律：验证类干预的结构性天花板（2.5 页）

- 12.1 六个独立设计的验证类机制，全部失败或归零：

  | 机制 | 干预方式 | 结果 |
  |---|---|---|
  | E1 strict verified-final | FINAL 必须等于最近成功执行的 SQL | 恢复 0 / 退化 3，成本翻倍 |
  | E4-A QueryPlan | 生成 SQL 前强制输出结构化计划 | −6 题，**目标类别反而变差** |
  | 字面量核实提醒 | 未经 `sample_values` 核实的字面量比较时软提示 | N=44 分层，**0 恢复 / 4 回退** |
  | JOIN 精简提示 | 协议加「只连必需表」 | N=26，v1 净 +1、v2 净 0；发现「脆弱题」噪声 |
  | E6 空集触发反馈重投 | 确定性机械测量喂回再答 | 与纯重试**统计上无法区分** |
  | 强制复核门控 | `LIMIT 1` 但实际多值 → 执行结果作为新 observation 喂回 | 23 题真的改了 SQL，**恢复 1 / 打坏 9 = 净 −8** |

  > ⚠️ **口径不一致，动笔前必须统一**：`REPORT_2026-08-11.md` 的「五次」= 前五行；
  > `reasoning_trace_findings_2026-08-12.md` 的「五次」= 前四行 + 门控复核。
  > 合并后实为 **6 个独立实验**。正文用 6，脚注说明历史文档的两种数法。

- 12.2 **统一解释：ReAct 循环有效性测量**（全 197 题，非只失败题，纯离线）：
  - 循环**有效但极端二值**：正确题恢复率 4–14%（4/77、3/69、9/66），
    **错误题恢复率三次运行精确为 0**
  - **99% 以上的失败题全程从未执行出匹配 gold 的结果**（1/120、1/128、2/131）——
    **循环没有可救的对象**
  - 模型**不会自适应增加探索**：执行次数 1.22 vs 1.38，多次执行占比 27.3% vs 30.0%，
    8 轮预算实际只用 1–2 轮 → **它不知道自己不知道**
  - **约 2/3 的正确答案，其提交的 FINAL SQL 从未被执行验证过**（正确题仅 31–36% 验证过，
    9–20% 全程未调用 `db.execute`）——**顶层 README 对 harness 的描述只覆盖约三分之一的正确答案**
- 12.3 **91.1% 的失败在第一版草稿即定型**（逐轮回放，真实执行每一版 SQL）：

  | | 题数 | 占比 |
  |---|---:|---:|
  | 从第一版草稿就错，全程没对过 | **143** | **91.1%** |
  | 中途出现过正确版本、最终又改错 | 7 | 4.5% |
  | 第一版正确、后来改错 | 4 | 2.5% |
  | 全程无可执行 SQL | 3 | 1.9% |

  平均 2.3 轮、13.1 个推理段的后续探查**几乎从不改变对错**
- 12.4 **时序律的正式表述**：ReAct 作为**承诺之前的落地取证**有效（+9.0）；
  作为**答案已有之后的挽救**无效（`Post-answer verification prompt` fixed 0 / broke 3；
  `Blocking FINAL until exploration` fixed 0 / broke 8）。
  所有失败机制都属于后者
- 12.5 **一个未检验的替代解释，必须写进正文**：历史上失败的 Prompt 机制**全部是含糊措辞**
  （`consider whether DISTINCT is required`）。两次独立观察显示措辞改为确切时行为剧变
  （违反计数 **19→4**；leaf 查库率 **0% → 94%**）。
  **「机制无效」与「措辞无效」尚未分离**——本文最该承认的 threat to validity

### 13. 推理轨迹层面的证据（1.5 页）

**主张**：把结论从「结果层统计」推进到推理过程本身（回应 8/11 Praktikum 上 Harshal 的要求）。

- 13.1 方法与规模：Responses API + `reasoning.summary=detailed`，**496/498 题全量抓取**；
  1640 个候选转折点；轮次级反事实重采样 20 案例 / 100+ 次
- 13.2 **方法论边界（如实写）**：做不到句子级重采样（隐藏推理状态不可编辑，接口限制非成本限制）；
  做不到 receiver head 分析（闭源 API 不开放 attention）
- 13.3 决策点信息增益排序：**六个新的轨迹结构特征里四个进前十一**，
  第 2 名「结果形状」信息增益 0.0454、答对率极差 55.3% ——
  从推理内容挖出的判断点信息量不亚于纯 SQL 语法特征
- 13.4 旗舰案例 `bird_959`（唯一真正的 thought anchor）：第 1 轮**在看到任何数据库结果之前**
  已写好 FINAL；重采样第 2 轮 6/8 采纳新证据改变方向，**但 8/8 仍答错**
- 13.5 **「结果形状」是统计强、机制异质的桶**（20 案例全部因果验证）：
  真正可复现的模型缺陷仅 20–25%，约 20% 是重采样即自愈的噪声，约 15% 是 gold 的问题
- 13.6 高调用次数**不可复现**：原 15–18 次的三题，重跑范围 1–11 次，从未接近原值 →
  极端调用次数是异常值，不是题目难度的固有属性
- 13.7 **答对/答错的推理阶段构成几乎相同（最大差异 2.5pp）** → **不存在可针对性修正的
  「错误思维模式」**；但失败题**明确表达不确定的频率高 15.8pp**（38.7% vs 22.9%）——
  **模型知道自己在猜**（这是 §19 多候选选择器的先验来源）
- 13.8 6492 个推理段中仅 **6.8%** 用于取证，93% 用于斟酌写法

## 第四部分：测量本身

### 14. 确定性后处理与「改形状 / 改语义」判据（2.0 页）

- 14.1 **受控对照（本项目最干净的一例）**：同一批 train 挖出的约定，两种交付方式

  | 交付方式 | 效果 |
  |---|---|
  | 写进 Prompt（`e3-ac` = e3-c + 静态 patterns，唯一变量） | **0**（违反计数 24 vs 25；DISTINCT 违反 14 vs 14） |
  | 由 后处理确定性改写最终 SQL | **+5 题**（两次独立测量一致），dev500 上 **+6** |

  → **系统侧确定性干预可复现，模型侧干预被噪声淹没**。
  机理：这三条不是模型缺失的知识，而是 BIRD 的书写偏好，且偏好在语义上是不占理的一方
- 14.2 三条约定的 train 支持度（**条件比率**而非语料频率）：分列不拼接 99.99%（69/69 库）、
  最值 `ORDER BY...LIMIT` 90.34%（63/65）、计数遇 JOIN 不去重 89.10%（65/67）
- 14.3 **反转（2026-08-16）**：用外部独立修正版 gold 逐条重测

  | 规则 | 改的是什么 | 命中 | 净 | 处置 |
  |---|---|---:|---:|---|
  | `count_no_distinct` | **计算语义**（COUNT 对象从实体变成行） | 29 | **−16** | 关闭 |
  | `no_select_concat` | **输出形状**（拼接拆两列，数据一字节没变） | 9 | **+8** | 保留 |
  | `superlative_order_limit` | **计算语义**，且会丢 WHERE 条件 | 2 | **−2** | 关闭 |

  **关掉两条、保留一条 = +18 题**（全删只有 +10）
- 14.4 **判据**：**输出后处理可以规整输出格式，不可以改变查询算的是什么。**
  这条判据**不做实验就能事前预测上表**，并解释了为什么「用 gold 支持度做门槛」会失灵——
  **支持度只能说明标注者多常这样写，不能说明这样写是对的**
- 14.5 `count_no_distinct` 是怎么烂掉的：修正版 gold 把 DISTINCT 使用从 83 题提到 130 题（+57%）。
  最干净的例子 `bird_1505`：模型写对 → harness 改错 → 原始 gold 也错（同一个错）→
  **两个错互相抵消，判「对」**。gold 一修好，抵消消失
- 14.6 **独立复现**：同一改动在另一批模型 SQL（`iter15`，`max_iterations` 8→15，444 题）上
  同样是**正好 +18** → 不是对 run1 的过拟合。
  **同一改动在原始 gold 上 −2、在修正 gold 上 +20 ——评测基准的正确性先于任何调优**
- 14.7 性质说明：`no_select_concat` 的 +8 **本质上是评测器的产物**；更本质的修法是在评测器里
  归一化拼接，但那会改变评分口径、与公开 BIRD 结果不可比

### 15. 基准质量：163 道全量定责与外部修正版复核（2.5 页）

**核心不是「gold 很烂」，而是「我差点用自己写的修正答案证明了一个错误结论」。**

- 15.1 逐步收紧的四轮审计（要按时间顺序讲，这本身是方法论）：

  | 轮次 | 范围 | 模型真实推理错误 |
  |---|---|---:|
  | F-Audit（2026-08-07，两轮） | 20 题抽样 | 30%（gold 缺陷 40%） |
  | 稳定失败审计（08-08） | 77 条中抽 31 | 约 10% |
  | 全量普查（08-08） | 当前最优配置全部 115 条失败 | **8.7%** |
  | 最终定责（08-16） | dev500 全部 **163 条** | **11.7–12.9%** |

- 15.2 **最终责任归属**（163 道全覆盖，150 道逐题人工判读）：
  gold **61（37.4%）** / 题面歧义 35 / **模型 30（18.4%）** / 双方 16 / 评测口径 9 /
  **后处理改写 6** / 不可评分 4 / 基础设施 1 / 题面缺失 1 → **gold : 模型 ≈ 2.0 : 1**
- 15.3 gold 缺陷的**六类可复用机制**：漏答题面明确要求的部分 / AND-OR 缺括号条件退化 /
  文本列当数值排序 / NULL 在 ASC 排最前被取到 / join 扇出放大聚合 / 答成另一个问题。
  最有说服力的一对：`bird_1404` 与 `bird_1422`（同库同两列，**gold 两次各取与题面相反的那一列**）
- 15.4 三个用不同方法、不同层面独立得到的比值一致：表选择层 **20 : 2**、
  公式类谁遵守 hint **9 : 2**、WHERE 条件增删 **9 : 1**
- 15.5 **表选择类的决定性证据：不是检索的问题**。33 题逐一核对：未检索到 **0**、
  检索到但未选中 **0**、**检索到、已选中、模型却没用 37/37**
- 15.6 **两个干预性实验（把观测性证据升级为因果证据）**：
  - **反事实消歧**：只改写歧义名词，命中预期指代对象 **1/7 → 6/7**，整题转正 0/7 → 2/7
  - **Hint 消融**：定向三臂 **0/5 → 3/5，对照组零损害**；
    **但全集消融（检测器命中 89/500）为 49/89 → 37/89，净 −12，投影 67.40% → 65.00%**。
    **两者不矛盾：hint 总体有用、局部有毒**；并顺带否证了一个相关性——
    含公式 hint 的题 55.1% vs 其余 70.1% 的 **15 pp 差距是难度标记，不是 hint 造成的**
- 15.7 **外部独立修正版复核 —— 本文最重要的一次自我修正**：

  | | 题数 | 准确率 |
  |---|---:|---:|
  | 原始 BIRD gold | 335/498 | 67.27% |
  | **独立修正版 gold（另一团队撰写，未看过我们的 SQL）** | **334/498** | **67.07%** |

  **两版 gold 语义不同的有 132 题（26.5%），准确率几乎没动：新判对 38、原对变错 39，净 −1。**

  - **推翻了什么**：「标注噪声在净额上压低了我们的分数」**不成立**，噪声两个方向对消。
    自修 gold 的 80.7% 与剔除不可评分的 67.95% 都在暗示「真实水平更高」，**这个暗示被外部数据否定**
  - **暴露了什么**：本文只审计失败题，**看得见坑我们的那一半，看不见送分的那一半**——**结构性偏差**
  - **证实了什么**：判别力梯度——我判 `gold` 的 61 道有 **84%** 被对方独立修正，
    `双方` 81%、`题面歧义` 46%、`模型` **25%**、我们本来答对的题 **12%**
  - **修正了什么**：自修 gold 让 61/61 全判对，换外部修正 gold 只有 **29/61**（改写前 SQL 34/61）。
    **我自己写的修正 gold 里约一半是朝模型答案拟合的——循环风险是真的，现在有了数字**
- 15.8 **机械判定第四次被证伪**：答案级两条方向性规则，11 道复核 **6 道判反 → 不得再使用**
- 15.9 判定的三档精度（机制级已执行验证 ~36 / 止于差异描述 51 / 仅答案级机械规则 13）

### 16. 撤回台账与由此固化的实验纪律（0.75 页）

- 16.1 **本项目撤回过的结论清单**（正文列表 + 附录全表）：见 §5 台账
- 16.2 **五条实验纪律**，每条都由一次未遂的错误结论固化：
  1. 凭证经 `resolve_llm_config`、路径经 runner 常量，不自行推导
     ——曾因直接读环境变量导致 10 题全 `APIError` 被记为「递归无效」
  2. **异常一律不得吞为结果值**，基础设施失败单独记账
     ——「静默失败伪装成实验结论」出现过至少两次
  3. **触发集实验至少重复 3 次**——单次观测在两个方向上都骗过人
  4. **优先采用不经过评分的指标**（违反计数、查库率、表召回率）——不受运行方差影响
  5. **manifest 记录生效值而非请求值**——`temperature=0` 这个缺陷藏了整个项目周期
- 16.3 一条独立的方法论要求：**任何「两条 SQL 是否等价」或「gold 是否有误」的判断
  必须实际执行比较结果集**——仅凭阅读 SQL 的判断被随后的执行推翻过（3/3）

## 第五部分

### 17. Discussion（1.25 页）

- 17.1 **为什么分界线恰好落在「谁来行使」上**：模型缺的不是能力，也不是工具——
  E5 证明信息完全可达（197/197 等价、5.36 次/题主动读取）、E6-v5 证明 leaf 真的会查库（94%）、
  E2-B 证明工具边界干净（110 事件 0 越权）。**缺的是「何时该用」的判断**：
  模型在将要答错时的探索强度与答对时无差别（§12.2），失败题的自检恢复率恒为 0。
  这与 SQRL 的论证吻合——**inspection 决策是训练习得的能力，不是给了工具就会用**。
  凡是把这个判断交还给 harness 的干预都兑现，凡是留给模型的都不兑现
- 17.1b **RLM 的哪些前提在本任务上不成立**：三个能力各自针对一个约束
  （上下文容量、执行不可信、单步推理不足），而这三个约束在「小 schema + 强推理模型 +
  可执行数据库」的组合下都不紧。这是任务属性，不是实现问题——
  也因此可以预测**它们何时会重新成立**：schema 更大、证据更长、需保留长历史时能力一的访问侧回来；
  模型可训练或具备可靠不确定性自评时能力三的前提回来
- 17.2 与 SQRL 的对照收束：**同架构 + 训练 = 突破；同架构 + 仅指令 = 天花板**
- 17.3 对基准使用者的建议：**在此类基准上报告的机制收益，必须先扣除数据集缺陷与标注对齐的部分**，
  否则会把「学会模仿标注习惯」误报为「提升了 Text-to-SQL 能力」
- 17.4 现在还剩什么可做：

  | 方向 | 覆盖 | 需要什么 |
  |---|---:|---|
  | 修 后处理的两条改写规则 | 6 道 / +1.2pp | 纯代码改动（已完成） |
  | schema 消歧 + 输出约定提示 | 歧义 A 类 9 + B 类 6 = **15 道** | 提示工程 |
  | **多候选 + 执行反馈选择** | 纯模型错 ~19 + 歧义 C/D 一部分 | **未实现**；先验已量化 |

  依据：**同配置两次运行逐题翻转 32 题、oracle 73.42%——多样性已存在，只是从未被利用**

### 18. Threats to Validity / Limitations（1.0 页）

1. **采样从未固定**，±3 pp 不可通过配置消除
2. **多数配置只跑一次**，小于 3 pp 的变化只能记为趋势
3. **隐藏推理不可见**（约 93% completion token），句子级归因不可行
4. **含糊 vs 确切措辞未被分离**（§12.5）
5. **定责只审计失败题**，看不见送分题（已量化为 39 道）
6. **不可外推到别的数据集/split**：163 道里三个库占 38%，且这三库 gold 质量明显低于均值
7. **61 : 30 不可用于「模型已接近上限」的论证**——它判的是责任归属，不是能力边界
8. **legacy 时代运行不可复现**：没有 manifest、没有 trace，结果文件连 `agent_profile` 都没有；
   5.2 pp 差距的归因做了三次推断、前两次被数据否定
9. **`max_iterations` 是保留的混淆项**（legacy 默认 15，clean 统一 8，legacy 实际值无从查证）
10. 两个已知对任意 Prompt 扰动敏感的「脆弱题」（如 `bird_1480` 在两个完全不同的机制下同症状回退）

### 19. Conclusion and Future Work（0.5 页）

三句收束：三能力的结论 / 时序律与判据 / 基准。future work 只写有量化先验支撑的两条：
**多候选生成 + 执行反馈选择**（Agentar 消融显示「生成+选择」值约 10.5 分，**本项目一分未取**），
以及它与「强制结构约束式递归」共同需要的前置条件：**构建一个能力失败密度更高的评测集**
（把已有的 gold 缺陷检测器与 hint 矛盾检测器跑到全集、剔除命中题，几乎不消耗 token）。
