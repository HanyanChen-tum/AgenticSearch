# DB-RLM Experimental Summary Report (2026-08-11)

Dataset: BIRD mini-dev, 500 questions across 11 databases. Model: `azure/seminar-gpt-5.4-mini`, with `temperature=0`, `reasoning_effort=high`, `max_iterations=8`, and train-only few-shot retrieval with `k=1`.

**All reported results use the official BIRD set-comparison metric** (`shared/evaluator.is_correct`).

---

| Configuration | Accuracy | Notes |
|---|---:|---|
| Baseline 2: keyword-based table filtering | 51.60% | Naive pruning is counterproductive |
| **Baseline 1: single-pass schema-to-SQL** | **55.20%** | No tools or iterative loop; **primary baseline** |

## 2. Effective Mechanisms

### 2.1 Offline Schema Context (E3-C): +3.20 pp

The full schema previously injected for every question is replaced with **deterministically retrieved, question-relevant context**: table and column descriptions, the PK/FK graph, join cardinality and fan-out, and value formats. Tables not selected by the retriever are represented only in a names-only index.

- Adversarial subset of 197 questions: +4.82 pp; full 500 questions: +3.20 pp
- Table recall: 98.4% (492/500); accuracy was actually higher on the eight questions with missed tables
- Cost: +14.29% tokens per question

### 2.2 Annotation-convention post-processing: +6 questions on the full 500

SQL-writing conventions were mined from the training pool (9,428 examples across 69 databases). The harness then **deterministically rewrites** the final SQL:

| Convention | Training support | Applicable examples | Databases with majority compliance |
|---|---:|---:|---:|
| Separate columns instead of concatenating with `\|\|` | 99.99% | 9,428 | 69/69 |
| Express extrema with `ORDER BY ... LIMIT` | 90.34% | 1,542 | 63/65 |
| Do not apply deduplication to counts involving a JOIN | 89.10% | 2,377 | 65/67 |

- +5 questions on the 197-question subset, consistently across two independent measurements; +6 questions on the full 500
- Triggered on 49 questions: corrected 11 answers and broke 5

### 2.3 Prompt rules audited on training data: +2.80 pp

The legacy prompt contributed +6.40 pp but is labeled `legacy-eval-tuned-unaudited`. After validating every rule against the training data, **two rules were accepted and two rejected**:

| Rule | Training support | Accepted? |
|---|---:|:--:|
| Use `ORDER BY ... LIMIT` for extrema, not `= (SELECT MAX ...)` | 90.3% (n=1,542) | ✅ |
| Project only one column for a single-part question | 84.5% (n=8,693) | ✅ |
| Return literal YES/NO for yes/no questions | **41.0%** (n=39) | ❌ contradicted by training data |
| Project multiple columns for multi-part questions | **28.6%** (n=595) | ❌ contradicted by training data |

Mechanism-level validation without scoring: incorrectly expressed extrema fell from **19 to 4**, and over-projection on single-part questions fell from **81 to 70**.

## 3. Negative Results

### 3.1 All five verification-oriented interventions failed

The five interventions were:

| Intervention | What it did |
|---|---|
| **E1 strict verified-final** | A hard state gate blocked `FINAL` unless the submitted SQL was exactly the same as the most recently executed SQL and that execution completed without an error or empty result. The model was sent back into the ReAct loop until it executed and resubmitted the exact final query. |
| **E4-A QueryPlan** | Before writing SQL, the model had to produce a structured JSON plan specifying the target entity, answer grain, schema links, required tables and joins, filters, aggregation, ordering, output columns, and expected result shape. After each database observation, any change required an explicit plan revision before another SQL execution. |
| **Literal-verification reminder** | A non-blocking warning was added when SQL compared a column with a string literal but the model had not called `db.sample_values` on that column. It asked the model to verify the stored encoding, casing, or date format before relying on the literal. |
| **JOIN-minimization prompt** | A fixed instruction told the model to include only tables required for an output column, filter, or relationship. A second version clarified that minimizing the number of joined tables must not change a necessary `LEFT JOIN` into an `INNER JOIN`. |
| **E6 feedback and resubmission** | When the submitted query returned an empty/all-`NULL` result or an error, the model received one additional attempt. The compute-control arm was told only that the previous SQL had returned no result; the feedback arm also received a deterministic report showing which top-level filter, when removed, restored rows. |

Root cause: across three full-run trajectory audits, the number of wrong-to-correct recoveries after an incorrect execution was **exactly zero**. More than 99% of failed questions never produced an execution result matching the gold answer at any point in the trajectory. In the smaller E6 trigger-set experiment, each retry arm produced only one one-off correction across three repetitions, on different questions, while also damaging correct answers; the effect was indistinguishable from resampling noise.

**Important qualification:** this does not mean that ReAct is useless. `findings.md` records a **+9.0 pp** gain from the ReAct loop combined with live database tools. The distinction is temporal: **evidence gathering before committing to an answer is effective; rescue attempts after an answer already exists are ineffective**.

### 3.2 RLM recursion: zero net gain on delegated questions across five iterations

| Version | Change | Leaf database-query rate | Net gain on invoked questions |
|---|---|---:|---:|
| v1 | Text-only leaf | — | 0 |
| v2 | Leaf can query the database | 0% | 0 |
| v3 | Database querying required | 0% | −2 |
| v4 | Schema supplied to leaf | 23% | 0 |
| v5 | Exact code example supplied | **94%** | **0** |

In v5, leaf agents did query the database and returned correct facts: `"Business"`, `"Closed"`, and `"2019-09-12"` were all genuine query results. The mechanism therefore worked end to end, yet its **net gain remained zero**.

**Structural explanation:** the parent already has access to `db.execute`, so anything the leaf can retrieve is also directly available to the parent. **Delegation creates no new information.**

This is structurally equivalent to E5-A, where context utilization was only about 4% because the constraint targeted by externalization did not exist. Neither of the two classic motivations for recursion applies to this task.

**Key finding:** none of the project's previous “RLM capability” experiments actually tested recursion itself. The recursion primitive had always been available in the REPL, but **no prompt ever mentioned it**, and it was invoked 0 times across 197 questions.

### 3.3 Static query patterns and Query Mining

Here, **static query patterns** refers to E3-A's `train-static-v1`: a fixed SQL-writing checklist manually distilled from the BIRD training pool and injected unchanged into the prompt for every question. Its eight rules cover aggregation grain, filtered aggregation, Top-K ordering, requested output columns, conditional scalar answers, `DISTINCT`, join paths, and window ranking. It does not retrieve patterns for the current question or model their support, applicability boundaries, counterexamples, or cross-database validity. It is therefore a static prompt prototype, not full Query Mining. **Query Mining** instead attempts to extract supported structural patterns automatically from training question–SQL pairs and retrieve only patterns relevant to each question, subject to cross-database validation gates.

- Combining E3-A static patterns with E3-C yielded 70/197, below E3-C alone at 77/197. However, the difference is within run-to-run variance, so the only justified conclusion is that the expected gain was not observed.
- Query Mining v2: none of the 28 slots passed the cross-database gate; the best slot outperformed the model's own judgment by only 1.5 pp.

## 4. Benchmark-quality Findings

We manually audited **all 115 failures** of the current best configuration on the 197-question adversarial subset; this was a complete census, not a sample.

| Root cause | Questions | Share |
|---|---:|---:|
| Defective gold answer | 44 | 38.3% |
| Unspecified output convention | 22 | 19.1% |
| Referential ambiguity | 18 | 15.7% |
| Contradiction between hint and gold answer | 14 | 12.2% |
| Residual annotation conventions | 7 | 6.1% |
| **Genuine model reasoning error** | **10** | **8.7%** |

Systematic gold-answer defects include AND/OR precedence bugs, tautological conditions, inflated counts caused by joins through `postHistory`, and gold queries that time out or return `None`.

**Implication:** this adversarial subset is no longer suitable for evaluating capability-oriented mechanisms, because 91% of its failures are not capability failures.

## 5. Methodology

### 5.1 Same-configuration rerun variance: 6 questions (3 pp)

Two runs with identical hyperparameters scored 77/197 and 71/197. Ten question-level outcomes flipped, while only **10.7% of SQL outputs were textually identical**. Setting `temperature=0` does not make outputs deterministic because approximately 93% of completion tokens are hidden reasoning tokens that differ between runs.

**Consequently, one earlier conclusion is withdrawn:** a seven-question drop for e3-ac was previously interpreted as evidence that static patterns were harmful. Because −7 exceeds the observed noise by only one question, that conclusion is unsupported. The significance threshold has been raised from 2 pp to 3 pp.

### 5.2 Vague versus explicit wording

Two independent validations from this round show the same effect:

| Mechanism | Vague wording | Explicit wording | Effect |
|---|---|---|---|
| Convention rule | `consider whether DISTINCT is required` | `Do not write WHERE col = (SELECT MAX...)` | Violations: 19 → 4 |
| Leaf database query | `you may use db.execute` | A directly reusable code block | 0% → 94% |

All four historically unsuccessful prompt mechanisms used **vague wording**. The mechanisms themselves may not be ineffective; their wording may be. **This hypothesis has not yet been tested.**

### 5.3 Experimental discipline established after two near-miss false conclusions

1. Resolve credentials through `resolve_llm_config` and paths through runner constants; do not derive them independently. Reading environment variables directly once caused all ten questions to return `APIError`, which was initially recorded as “recursion is ineffective.” Deriving the database path independently once made post-processing appear to cause a −3 regression.
2. **Never absorb exceptions into result values.** Infrastructure failures must be tracked separately.
3. **Repeat trigger-set experiments at least three times.** A single run once appeared to show successful recovery; three repetitions showed that it occurred in only one of the three runs.
4. **Prefer metrics that do not depend on scoring**, such as violation counts, database-query rates, and invocation rates. These are not affected by run-to-run scoring variance.

## 6. Current Status and Next Steps

**Current best reproducible configuration:** `e3-c-conv-rules` = Offline Schema Context + convention post-processing + training-audited rules, achieving **67.40%** with a fully auditable end-to-end manifest.

Three candidate directions, ordered by strength of evidence:

| Priority | Direction | Evidence | Cost |
|---|---|---|---|
| A | Systematize the shift from vague to explicit wording and rewrite previously failed prompt mechanisms | Two independent validations in this round | About 2 hours each |
| B | Hint-targeted ablation; detector matches 92 of the 500 development questions | Three-arm experiment improved from 0/5 to 3/5, with no damage to the control group | One run |
| C | Continue auditing untested legacy-prompt rules and output-column ordering conventions | Existing audit tools | Zero-cost analysis first |
