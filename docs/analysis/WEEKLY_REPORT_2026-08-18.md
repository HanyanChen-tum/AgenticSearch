# 本周报告：因果分析如何改进了系统（2026-08-12 ~ 08-18）

一句话概括：**这周最大的改进不是让模型更聪明，而是发现「尺子是坏的」，
并沿着因果链把坏掉的部分逐个定位、修好、重测。**

---

## 零、先看结果

在**外部独立修正版 gold** 的 dev500（498 题）上，五层对照链：

| 层 | 配置 | 新增的是什么 | 准确率 |
|---|---|---|---:|
| 0 | B1 | —— 零方法：单次生成，无探索/无纠正/无重试 | **70.3% / 70.1%** |
| 0' | B2 | + 关键词表预筛 | 66.7% / 67.7% |
| 1 | `clean-e0` | + agent 工具循环 | 进行中 |
| 2 | `e3-c-noconv` | + 离线 schema 检索与元数据 | **85.3%** |
| 3 | `e3-c-conv-rules` | + convention 后处理 | **86.7% / 86.7%** |
| 4 | `e3-c-recursive-db` | **+ RLM 递归** | **86.1%** |

B1 两次只差 1 道（噪声 0.2pp），是可靠的地板。
从 70.2% 到 86.7% 的 16.5pp，**主要发生在第 1→2 层**（agent 循环 + 检索）。

## 一、递归（论文主题）：全集 −0.6pp，调用子集 +2 道

| | 题数 | L3 无递归 | L4 有递归 | 差 |
|---|---:|---:|---:|---:|
| 全集 | 498 | 86.7% | 86.1% | **−3 道** |
| **递归实际被调用** | **74（14.9%）** | 85.1% | **87.8%** | **+2 道** |
| 未调用递归 | 424 | 87.0% | 85.8% | −5 道 |

**三个必须同时报的事实：**

1. **递归只在 14.9% 的题上被真正调用。** 全集效应被 85% 的无关题稀释。
2. **调用子集上 +2 道，但那只有 74 题。** 而干净的同配置重复测得**逐题翻转 20/480**——
   +2 完全落在单题抖动范围内，**不能称为效应**。
3. **未调用递归的 424 题上 −5 道。** 那里没有递归，差异只能来自 prompt
   （`conventions-recursive-v1` vs `basic-conventions-v1`）——这是设计上消不掉的混淆：
   prompt 不点名递归工具，模型就不会调用它（历史记录：197 题 0 次调用）。

**结论：本轮数据不支持「递归提升了准确率」，也不支持「递归有害」。有效样本太小。**
论文若要论证 RLM 的作用，需要的是**提高调用率**的设计，而不是在 14.9% 的调用率上找效应。

## 二、因果链：每一步都是「发现缺陷 → 定位 → 修 → 重测」

### 第 1 步：逐题判读 163 道失败，发现尺子有问题

不做汇总统计，逐题读【题面】【hint】【双方 SQL】【双方执行结果】，必要时下探数据库跑反证查询。

结果：**gold : 模型 = 61 : 30**。gold 侧缺陷是最大单一来源。

其中约 27 道是**执行即可证伪、与读题无关**的 SQL bug：

| 机制 | 实例 |
|---|---|
| AND/OR 缺括号导致条件退化 | `bird_1265` gold 算出 47，正解 35 |
| 文本列当数值排序 | `bird_879` 取到 `'91.610'`，真实最大 257.32 |
| NULL 在 ASC 排最前被取到 | `bird_847` 取到无成绩的车手 |
| join 扇出放大聚合 | `bird_198` 得 732.1，正解 20.25 |

### 第 2 步：用外部修正版 gold 交叉验证，把「换尺子」和「重新采样」拆开

关键设计：同一批题上出三列。

| 列 | 模型答案 | 判分标准 |
|---|---|---|
| A | 原答案 | 原 gold |
| B | **同一份原答案** | 修正 gold |
| C | 新运行答案 | 修正 gold |

`B − A` 是纯「参考答案改了」的效应，`C − B` 是纯「重新采样」的效应。

| | 干净子集 277 | **纯 gold 修正 74** |
|---|---:|---:|
| A 原答案 × 原 gold | 81.9% | **50.0%** |
| B 原答案 × 修正 gold | 87.7% | **71.6%** |
| C 新运行 × 修正 gold | 86.3% | 70.3% |
| **换参考答案的贡献** | **+16** | **+16** |
| 重新采样的贡献 | −4 | −1 |

**74 道纯 gold 题上，模型答案一个字节没变，判分从 50.0% 升到 71.6%。**
原始 gold 在这 74 道里判错了 16 次，而模型本来就是对的。

而且由错变对的 26 道里，**19 道正是第 1 步独立判为 `gold` 的题**——
读题面 + 执行反证、另一团队独立重标、模型答案不变而判分翻正，三条证据线汇合。

### 第 3 步：发现 harness 规则在拟合坏 gold

`count_no_distinct` 规则在 JOIN 查询里从 `COUNT` 删除 `DISTINCT`，
依据是 train gold 上 2377 样本、69 库、**0.891 支持度**，看起来无可辩驳。

但修正版 gold 把 DISTINCT 的使用从 83 题提到 130 题（**+57%**）。
**那 0.891 度量的不是 SQL 语义，是标注者系统性漏写 DISTINCT 的习惯。**

最干净的例子 `bird_1505`（题面 "how many **customers**"）：

```sql
模型写的（对）    SELECT COUNT(DISTINCT T1.CustomerID) ...
harness 改成（错） SELECT COUNT(T1.CustomerID) ...
原始 gold（也错）  SELECT COUNT(*) ...
```

**规则的错和 gold 的错互相抵消，于是在原始 gold 上判「对」。**
这解释了三件此前对不上的事：为什么该规则在原始 gold 上测出净正、
为什么它自己造成 5 道失败、为什么换修正 gold 后新增失败集中在实体计数题。

**处置与判据：** 关闭两条**改变计算语义**的规则，保留一条**只改输出形状**的。
判据写进生成脚本的 `SEMANTICS_CHANGING`，支持度再高也不再启用——
因为该脚本按支持度重算 `enabled`，只改产物会被下次重跑覆盖。

> harness 后处理可以规整输出格式，**不可以改变查询算的是什么**。
> 支持度只说明标注者多常这样写，不说明这样写是对的。

### 第 4 步：发现 harness 缺陷把自己的崩溃记成「模型答错」

本机控制台是 cp936，两处 `print()` 无 verbose 开关。数据库行里只要有一个编不出的字符
就抛 `UnicodeEncodeError`，异常穿出后被当作模型的真实失败，`correct=False` 落盘。

**`bird_847` 的 trace：模型查对了 `Räikkönen`，`ä` 编不进 cp936，于是记为答错。**

它**不是随机噪声，而是有选择性的**：被杀的是答案含非拉丁字符的题，
按数据库高度集中（`card_games` 12%、`formula_1` 8%），
**同时扭曲总分和任何按数据库、按难度的分层分析**。

修复后重跑，两个推理捕获臂各涨 **+2.2pp**，`arcwise_full` 从 84.5% 更正为 **86.7%**。

更深的一层：异常分类用**类名子串白名单**，凡类名不含 `API`/`Connection`/`Timeout`
一律记为模型答错。方向是反的——未预料的异常绝大多数是我们自己的代码崩了。
全仓审计发现 `NotFoundError` 200 条、`UnicodeEncodeError` 66 条、`BadRequestError` 33 条
都被静默记成了模型能力不足。

### 第 5 步：发现「噪声带」估计本身是错的

原本用两组重复运行估出「同配置噪声 1~2pp」。逐个核查后**两组都不成立**：
一组 `max_iterations` 是 8 vs 15（该字段不进 `agent_config_sha256`，所以 sha 相同但配置不同），
另一组两个文件的崩溃数不等（0 与 16），差值里含 harness bug。

**唯一干净的同配置重复**（修正数据集，两次完整运行，均已修复）：
两次都是 **86.7%，聚合差距 0.0pp**；**但逐题翻转 20/480**。

两条都要报：**配置级比较可以用很紧的尺子，逐题因果分析不能拿这个 0.0pp 当稳定性保证。**

## 三、一个被证伪的干预（负结果，但方法值得记）

读推理轨迹时发现：**22.8% 的题里模型声称「我不能执行工具/看不到结果」**，
这批题答对率低 12.5pp。假设是：模型因此放弃核实、改为猜测。

于是做了单变量 A/B：prompt 里加一句「这些调用真的会执行，输出会在下一条消息返回」。

**四步全部指向假设错误：**

1. 交互表显示四个格子的**实际工具调用率都是 94~100%** —— 它嘴上说不能执行，手上照样调，机制不成立
2. 「想核实」才是最强信号（−17.3pp），但那是**反向因果**——题难→不确定→才说要核实
3. 证据基础是**事后回放**的推理，可能对不上原始运行（模块 docstring 点名 `bird_93`：回放时查了库，原始运行没查）
4. A/B 实测：ctl 330 vs trt 326，**−4 道**，翻转 22/26 基本对消

**但有一个真实的副效应：加那句话让第一轮推理短了 22%（51.0 → 39.8 句/题），准确率不变。**
说明那部分推理是冗余的——在反复斟酌一件本来确定的事。

**方法上的教训：关键词启发式在这份语料上产出过两个自洽但错误的结论。**
自洽的文本叙事最容易骗人，断言真假要靠执行来定。
