# E6 受控递归：两个触发设计的实测结果（2026-08-09）

## 背景与设计约束

递归的三个常见价值主张，有两个已被本项目自身数据否定：

| 价值主张 | 本项目证据 | 状态 |
|---|---|---|
| 上下文管理（每个 leaf 看得更少） | 上下文利用率仅约 4%，E5-A 外部化是净负担 | 已否定 |
| 子结果验证 | 四类验证机制全败，ReAct 恢复次数三次运行恒为 0 | 已否定 |
| 更多计算 | 未测 | E6-A 等预算对照 |
| 结构约束 / 错误隔离 | 未测 | E6-B |

因此本轮只设计"结构约束"型递归，且**触发与分解一律由 harness 确定性决定**，不引入模型判断——这是与四次失败机制的关键区别。

另有一条来自 `findings.md` 的重要区分，此前在 `SYNTHESIS.md` 中被压缩得过度：

| findings 记录 | 增益 | 时序 |
|---|---|---|
| ReAct loop + live DB tools | **+9.0** | 承诺**之前**取证 |
| Post-answer verification prompt | fixed 0 / broke 3 | 答案**已有之后**自查 |
| Blocking FINAL until exploration | fixed 0 / broke 8 | 强制多转 |

"ReAct 恢复次数为 0"测的是第二类，不蕴含"ReAct 无效"。递归的反馈必须落在取证一侧才有先验理由。

## 触发设计一：粒度不变量 —— 未通过第 0 步

**规则**：查询做了排序取头部（`ORDER BY ... LIMIT`）、无 `GROUP BY`、无聚合函数，且 pre-LIMIT 候选行中实体有重复 → 粒度可疑。读模型自己的 SQL，不解析题目。

**定容结果**（零 token）：

| | 命中 |
|---|---:|
| 118 题稳定失败中 | **4** |
| 70 题稳定正确中（误报） | **2** |
| 精度 | 66.7% |
| 命中的模型真错 | 仅 `bird_1472` |

靶子 4 题，低于 6 题重跑方差。`bird_904` 是稳定答对的题，行/实体比高达 483x——比值大小也无法用于提纯。

**更根本的问题**：该机制假设"粒度正确 = 答案正确"。直接检验这个前提，统计"聚合建立在会扇出的 JOIN 行集上"出现在哪一侧：

| | 题数 |
|---|---:|
| 只有 pred 有 | 21 |
| **只有 gold 有** | **18** |
| 两边都有 | 29 |
| 两边都没有 | 46 |

**BIRD 的 gold 自身在近半数稳定失败中按扇出粒度聚合。** 扇出不是错误信号，强制"正确"粒度推离 gold 的次数与推向 gold 的次数相当。该触发设计据此废弃。

## 触发设计二：空集 —— 通过定容，进入实验

**规则**：最终 SQL 执行结果为空集/全 NULL，或执行报错。运行时可判，不需要 gold。

| | |
|---|---:|
| 运行时触发 | 10 题 |
| 其中当前判对（唯一下行风险，`bird_1526`，其 gold 本身为空） | 1 |
| 命中的模型真错 | 2（`bird_95`、`bird_1175`） |
| 两次运行都触发 | 5 |

**机械定位**：逐个摘掉顶层 WHERE 合取项并重新执行，找出致空条件。10 题中 **5 题定位成功**，且定位结果诊断精确——例如 `bird_95` 显示两个 `= (SELECT MAX(...))` 条件单独存在时分别有 547 行和 1 行，同时存在时为 0 行，即"最值合取"形态。

### 确定性处理：空集时解除守卫

`superlative_order_limit` 约定（train 支持度 90.34%）的保守守卫存在，是为了保护一个**能出结果**的查询。空集没有可保护的东西，因此空集是解除守卫的合法条件：把所有 `x = (SELECT MAX/MIN ...)` 合取项转为 `ORDER BY x + LIMIT 1`。

| 运行 | 触发改写 | 转正 | 打坏 | 净 |
|---|---:|---|---|---:|
| e3-c run3 | 3 | `bird_189` | — | **+1** |
| e3-c-conv | 3 | `bird_189` | — | **+1** |

两次独立运行完全一致，零打坏。

## E6-A / E6-B 实验

**等预算配对**：同一 10 题触发集，同一模型与参数，各多一次调用。唯一差异是第二次调用被告知什么。

- **Arm A**：「上次的 SQL 返回了空结果，重新写一遍」——只有额外计算
- **Arm B**：同上，外加机械定位报告（哪个条件去掉后有多少行）——额外计算 + 落地事实

每臂重复 3 次。基础设施错误单独记账，不计入转正率分子分母。

| 处理 | 有效调用 | 错题转正 | 对题打坏 | 净 |
|---|---:|---|---|---:|
| 确定性改写 | 确定性 | **1** | **0** | **+1** |
| Arm A（等预算，无事实） | 28 | 1 / 25 = 4.0% | 1 / 3 | 0 |
| Arm B（等预算 + 事实） | 26 | 1 / 23 = 4.3% | 2 / 3 | −1 |

参考基线（同配置重跑，无任何干预）：错→对 2/120 = 1.7%，对→错 8/77 = 10.4%。

### 结论

1. **两臂统计上无法区分。** 各自唯一一次转正都只出现在 3 次重复中的 1 次，且是不同的题（A 恢复 `bird_529`，B 恢复 `bird_1175`）。这是重新采样的特征。
2. **机械定位的事实没有带来任何增益。** 即使反馈内容是确定性测量、绝对可靠，相对纯重试仍无差别。
3. **两臂都更容易毁掉本来对的题**（33% / 67%，基线 10.4%），复现 `findings.md` 中 `Post-answer verification prompt: fixed 0 / broke 3` 的模式。
4. 同一批题上，**确定性改写是唯一可复现的正收益**。

这是本项目结构性结论的第五次确认，也是最严格的一次——前四次是设计不同的验证机制，本次连"反馈绝对可靠"这一条件都满足。

## 两次未遂的错误结论（方法论）

本轮实验先后产生过一个假阴性和一个假阳性，两者都几乎被写成定论。

**假阴性**：首次运行两臂均得「0 转正」，看似干净地否定了递归。实际是 10 题全部 `-- APIError`——脚本读 `LLM_API_KEY`，而本仓库 `.env` 使用 `api_key`/`azure_endpoint`/`deployment` 命名，正式 runner 经 `resolve_llm_config` 解析。更糟的是异常被吞成 SQL 字符串，**基础设施故障被记录为实验结果**。这与同期另一处 `data/dev_databases` 路径写错、使后处理看起来是 −3 的事故属同一类：**静默失败伪装成实验结论**。

**假阳性**：修复凭证后的首次运行中 `bird_1175` 转正、`bird_1526` 保住，看似支持"落地事实有效"。三次重复后显示 `bird_1175` 只在 1/3 的运行中转正——那次恰好撞在噪声上。

**由此固化两条要求**：

1. 实验脚本一律经 `resolve_llm_config` 取凭证，异常一律不得吞为结果值，失败即中止或单独记账。
2. **触发集实验必须重复至少 3 次。** 小样本单次观测在本项目中两个方向都能骗人。

## 否定的边界

本轮测的是**「反馈即文本」**形式的递归。**「强制结构约束」形式（leaf 1 必须实际执行、leaf 2 只能建立其上、中间结果不可绕过）从未被测试**，因为其确定性触发（粒度不变量）在定容阶段即被证明没有靶子。

| 递归形式 | 状态 |
|---|---|
| 反馈即文本 | **已测，无效**，与等预算重投不可区分 |
| 强制结构约束 | **未测**，触发条件在本数据集上无靶子 |

## 对后续的意义

在 197 题子集上，10 题模型真错中递归形态匹配的只有 2–3 题。**该集合已不适合评估能力型机制**——不是实现问题，是靶子问题。

要让递归有机会被公平检验，前置条件是**构建能力失败密度更高的评测集**：把已有的 gold 缺陷检测器与 Hint 矛盾检测器跑到 BIRD dev 500 全集，剔除命中题。该步骤几乎不消耗 token，此前列为可选，现升级为必需前置。
