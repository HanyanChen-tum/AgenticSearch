# 全 500 题基线对比与 5.2 pp 差距的归因（2026-08-09）

## 起因

E0 之后的全部实验都在 `bird_cleancore_ids.json` 的 197 题对抗子集上进行，**当前最优配置从未在全 500 题上跑过**，因此无法与项目早期基线直接比较。本文档补上这一跑，并记录随之暴露的一个未解差距。

## 一、评分口径：旧结果文件与 README 不是同一把尺

首次比较时把官方口径的新结果与存档 `correct` 字段的旧结果直接相减，虚增了改进幅度。旧运行使用严格的排序列表比较，`scripts/rescore_official.py` 的注释记录了这一点；README 的数字是官方集合比较（`shared/evaluator.is_correct`）重评后的。

统一到官方口径后：

| 运行 | 存档 `correct` | 官方口径 | 差 |
|---|---:|---:|---:|
| `bird_b1_azure_500` | 52.40% | **55.20%** | +2.80 |
| `bird_b2_azure_500` | 50.20% | 51.60% | +1.40 |
| `bird_ours_v4_500` | 61.20% | **64.20%** | +3.00 |
| 其余（含本次新跑） | — | 无变化 | 0.00 |

重评后与 README 完全吻合。**结论：比较任何早期结果前必须先重评，不能直接读 `correct` 字段。**

README 另记 `Clean 3-run ensemble 71.1%`（3 倍推理成本）与 `Best 5-run ensemble 72.3%`——后者 README 自行标注 `includes 2 runs w/ dev-pool retrieval (disclosed)`，即用 dev 集内容辅助答 dev 集，**可比性最差，不应作为对标**。

## 三、5.2 pp 差距：两个假设已被数据否定

### 假设一：`bird_reasoning_high_500` 使用了 `db_hints` —— 否定

`ours/db_hints.py` 是针对 eval 表现最差的三个库（california_schools、thrombosis_prediction、financial）手写的提示，内容具体到 `"For consumption totals: SUM(yearmonth.Consumption) grouped by CustomerID and filtered by Date"`——恰是 `bird_1472` 的标准答案。据此曾推测该运行的领先来自这一组件。

逐库准确率直接否定了它：

| 运行 | 三个 hinted 库 | 其余库 | 差 |
|---|---:|---:|---:|
| `bird_ours_v4_500` | 51.8% | 67.8% | −16.0 |
| `bird_trainfs_rhigh_500` | 50.9% | 73.7% | −22.8 |
| `bird_reasoning_high_500` | **55.4%** | **74.0%** | **−18.6** |
| `e3_c_conv_dev500_run1` | 51.8% | 68.3% | −16.5 |

**若注入了 db_hints，这三个库不可能仍是全场垫底。**

### 假设二：E3-C 的 schema 检索在全集上丢表 —— 否定

E3-C 将全量 schema 替换为按题检索，上限 8 表 / 每表 16 列（`_E3_F_V4_MAX_TABLES`、`_E3_F_MAX_COLUMNS_PER_TABLE`）。该上限只在 197 对抗子集上验证过。对全 500 题比对"gold SQL 所需表"与"检索实际选中的表"：

| | 题数 |
|---|---:|
| gold 所需表全部被选中 | **492（98.4%）** |
| 至少漏一张表 | 8（1.6%） |

且漏表的 8 题准确率 **87.5%**，高于未漏表的 64.1%。**表召回不是瓶颈。**（未选中的表仍获得 names-only 索引，漏表并不等于不可见。）

### 假设三：few-shot 差异 —— 先验不成立

README 自记 `+ high reasoning, no few-shot | 68.6% | ablation: retrieval not load-bearing`。完全去掉 few-shot 只降 0.6 pp，仍高于 64.60% 约 4 pp。

## 四、方法论记录

本轮对同一个 5.2 pp 差距连续做了三次推断，前两次被数据否定，其中"legacy 靠 db_hints 领先"一条曾被两次断言、两次收回。**停止推断，改为实验分离。**

这与本项目既有教训一致（`SYNTHESIS.md` §4.6）：任何关于"某运行为何更好/更差"的判断都必须实际测量，阅读配置文件或结果文件不足以支撑结论。此处的额外困难是 legacy 时代的运行**没有 run_manifest、没有 trace 目录、结果文件中连 `agent_profile` 字段都没有**，其配置已不可从产物恢复。

## 五、待完成：三方分离实验

超参与 `e3-c-conv` 逐项相同（`temperature=0`、`reasoning_effort=high`、`max_iterations=8`、`k=1`、同一数据集），**只切 `--agent-profile`**，因此差异可完全归因于 profile：

| profile | 状态 | 若结果为… |
|---|---|---|
| `e3-c-conv` | 已完成 **64.60%** | — |
| `clean-e0` | 运行中 | ≈69% → 差距全在 E3-C，即其在 197 上的 +4.82 pp **不泛化到全集**；≈64–65% → 差距在 clean harness 本身（prompt profile / 能力门禁 / 迭代上限） |
| `legacy-e0` | 运行中 | 补完 legacy → clean → +E3-C 的完整链路 |

**保留的混淆**：`max_iterations=8` 统一施加于三者，而 legacy 时代运行的该参数无从查证（`run_bird_indomain_fewshot.py` 的默认值是 15）。因此本实验能干净回答"profile 差异贡献多少"，但**不能**排除迭代上限也是差距来源之一。若三方均落在 64–65% 区间，下一步应单独测 `max_iterations`。

`legacy-e0` 启用 `use_db_hints=True`，其提示为观察 eval 失败后手写。该运行是**诊断用途**，其数字不构成可辩护的研究结论。
