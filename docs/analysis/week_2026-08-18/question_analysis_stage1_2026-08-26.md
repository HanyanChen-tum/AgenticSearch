# 阶段一结果：读题分析 −3.3pp，但失败原因不是模型不听话（2026-08-26）

承接 [`question_analysis_plan_2026-08-25.md`](question_analysis_plan_2026-08-25.md)。
实现见 `ours/agent/question_analysis.py`，profile `e3-c-recursive-db-qa`，
语料 `data/processed/phase_a_46.json`（46 道根因已知的失败题）。

## 一、结果：阴性，两次重复方向一致

| | 46 道上的正确率 |
|---|---|
| 基线 `e3-c-recursive-db`（两次） | 28.3% / 26.1%，均值 **27.2%** |
| 读题分析 `-qa`（两次） | 23.9% / 23.9%，均值 **23.9%** |
| | **−3.3pp** |

按两次合计逐题比较：**变好 4 道**（`bird_228`、`bird_32`、`bird_791`、`bird_1241`），
**变差 8 道**（`bird_1480`、`bird_1080`、`bird_637`、`bird_416`、`bird_640`、
`bird_1472`、`bird_85`、`bird_928`）。

**与 E4-A 的 −3.05pp 几乎同幅度**，而本次特意避开了 E4-A 的全部已知问题
（5 字段 vs 20 字段、只谈题意不谈实现、事前而非事后）。

## 二、机制侧：门控完美工作，所以阴性不是实现问题

| 检查 | 结果 |
|---|---|
| 产出有效分析 | **46/46（100%）**，两次运行都是 |
| 平均尝试次数 | **1.00** —— 没有任何一道靠重试，更没有触发放行兜底 |

**这条必须先确认，否则 −3.3pp 可能只是在测「模型会不会写 JSON」。** 它不是。

---

## 三、根因：这批题上模型本来就「看完题直接交卷」

这是本文最重要的发现，也推翻了计划里的隐含假设。

| | 基线 | 读题臂 |
|---|---|---|
| 平均消息数 | **3.35** | 5.22 |
| 消息数分布 | **38/46 道只有 3 条** | 42/46 道 5 条 |
| 查库事件（`db.*`） | **0 次** | **0 次** |

基线在 38/46 道上的完整轨迹是：system → question → `FINAL(...)`。
**一次工具都没调用。** 读题臂一样，只是中间多插了「分析块 + 已记录」这一来一回。

`bird_416` 的 5 条消息是最干净的例子：

```
[0] system      工具说明与约定
[1] user        题目 + hint + few-shot
[2] assistant   ```question-analysis {...}```
[3] user        "Analysis recorded. Now answer the question, following it."
[4] assistant   FINAL("SELECT ... COUNT(CASE WHEN ...) ...")
```

**中间没有任何探索、验证、或对照分析自查的环节。**

所以「模型读懂了题却没照做」这个说法不准确。更准确的是：

> **在一个「看完题直接交卷」的流程里，插入一段分析只是多了一段前文。
> 没有任何机制让它约束后面的生成——分析和 SQL 是两次独立的生成。**

这同时解释了 E4-A：它也是「先输出结构、再生成 SQL」，中间同样没有落实环节。
**两次失败共享同一个结构性原因，不是两个独立的坏设计。**

## 四、一处必须更正：我第一次的判读是错的

初次汇报时我说「6 道去重题分析 6/6 正确」。**那是关键词匹配的结果**
（`counting_unit` 文本里含 card/patient/entity 就算对），逐字读原文后是 **4/6**：

| 题 | run1 的 `counting_unit` 原文 | 判读 |
|---|---|---|
| `bird_1037` | "players (entities), because 'at least once' refers to a player-level condition" | ✅ |
| `bird_1241` | "Patients, counted as unique individuals rather than raw test rows" | ✅ |
| `bird_1243` | "Patients (unique people), not laboratory rows" | ✅ |
| `bird_383` | "Entities (cards), not table rows" | ✅ |
| **`bird_416`** | "cards; identical card records are counted as **separate rows** unless…" | ❌ **说的是按行** |
| **`bird_1169`** | "patients/entities rather than raw rows, **though the wording could be read as lab records**" | ⚠️ 自我怀疑 |

run2 同样：`bird_416` 只写了 "cards"（没给粒度），`bird_1169` 写 "however the hint's
calculation language refers to summing matching records"。

**而这 2 道正是最终 SQL 没去重、判错的那 2 道。**

这是本项目反复记录的同一类错误——**用机械匹配替代语义判读**——这次犯在我自己的
判读脚本上。修正后的分解：

| 情形 | 道数 | 说明 |
|---|---:|---|
| 分析就错了 | 2 | `bird_416`、`bird_1169` |
| 读对了也做对了 | 3 | SQL 确实用了 `COUNT(DISTINCT)` |
| 读对了没做对 | 1 | `bird_1037`，SQL 未去重但碰巧判对 |

## 五、结论与下一步

**1. 「让模型先输出一段分析」这个形态可以判定为已排除。**
两次独立设计（E4-A 重型、本次轻量）、相反的时序、字段数差 4 倍，**结果一致为负**。
再改分析的格式没有意义——问题不在格式。

**2. 但方向本身没有被否定。** `bird_1241` 被救回，正是「分析说实体 + SQL 真去重」那道。
**当分析真的约束了 SQL 时，机制是有效的。** 瓶颈在「落实」，不在「读懂」。

**3. 因此下一步是把分析变成可执行的校验，而不是一段前文。**

具体做法：分析里写了 `counting_unit = 实体`，就在提交 `FINAL` 时**校验**最终 SQL
是否用了 `COUNT(DISTINCT)`；不一致就带着具体理由打回重写。

这与 `keep_ties` / `printf_to_round` 是同一类做法——**在提交那一刻做确定性检查**——
而那两条恰恰是本周唯二有效的改动（离线回放 +7~+13 道）。区别在于：
那两条是无条件改写，这一条是**用模型自己的分析当判据**，所以不需要我们预先知道
每道题该怎么算。

**风险**：这是一个 FINAL 处的拦截，形式上接近 E1 `verified_final`（已被否决）。
区别是 E1 要求模型自己预先跑过一模一样的字符串、触发率 90%；这里只在
「分析说实体但 SQL 没去重」这一个具体矛盾上触发，预期触发率个位数百分比。
**这个区别必须实测，不能假定。**

## 六、边界

1. **46 道是失败题构成的人群**，基线只有 27.2%，与全集 88% 的行为可能不同。
   尤其「38/46 道不查库」这个现象，很可能是这批难题特有的，**不能外推到全集**。
2. 两次重复方向一致，但 46 道上 ±1 道就是 2.2pp，**−3.3pp 约等于 1.5 道**，
   量级很小。结论「阴性」可靠，「阴性有多大」不可靠。
3. 第四节的判读由我完成，仍是同一个 AI 系统内部的复核，未经独立校准。
