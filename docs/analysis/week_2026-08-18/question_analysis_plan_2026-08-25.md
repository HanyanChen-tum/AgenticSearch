# 计划：让模型先把题读明白，再写 SQL（2026-08-25）

依据 [`flatzero_23_root_causes_2026-08-25.md`](flatzero_23_root_causes_2026-08-25.md) 的
46 道逐题根因。本文只是计划，**没有任何实验数据**。

---

## 一、这条路的靶子有多大

按根因表逐类判断「事前读题分析能不能救」：

| 机制 | 题数 | 能救 | 理由 |
|---|---:|---|---|
| 聚合去重粒度 | 6 | **能** | 题面写了 "at least once" / "at least one record"，是读题就该抓的 |
| 漏掉或多加过滤条件 | 4 | **能** | `bird_48` 题面明说 merged，模型完全没写 |
| 少乘 100 | 3 | **能** | 题面写了 percentage |
| 语义误读 | 3 | **能** | 正是这一类 |
| 缺聚合步骤 | 2 | **能** | "monthly consumption" 要先 `GROUP BY` |
| 选错列或表 | 6 | 部分 | 2 道题面确有歧义，其余靠查证不靠读题 |
| 公式 / 分母口径 | 4 | 部分 | 分母该用什么，约一半能从题面读出 |
| 其它 | 3 | 部分 | |
| **类型/格式不匹配** | **11** | **不能** | 见下，这类要用别的办法 |
| 缺失值 / NULL 处理 | 4 | 不能 | 0 是哨兵值、NULL 排序——要看数据不是读题 |

**明确能救 18 道，加上部分可救最多 31 道 = +3.6pp ~ +6.2pp（全集 498）。**

对比一下量级：五层链里第 2 层（离线检索）是 +2.5pp，第 3、4 层加起来 +0.7pp，
并列改写实测 +1.4pp。**这是目前找到的最大的一个靶子。**

> 注意这是**天花板**，不是预期值。它假设分析每次都做对且模型照做，实际会低不少。

---

## 二、必须避开的三个已知坑

这条路不是没人试过，**前人失败的方式决定了这次该怎么设计**。

| 前例 | 结果 | 教训 |
|---|---|---|
| **E4-A QueryPlan**：强制 20 个必填字段才准提交 | **−3.05pp**，且**它的目标类别（聚合/排序）从 29 恶化到 33** | 那 20 个字段里有 `joins`、`filters`、`having`、`group_by`——等于逼模型在看数据之前把整条 SQL 用 JSON 写一遍。**那是提前提交实现方案，不是分析问题** |
| **事后复核 ×5**：`verify_before_limit` 等 | **五次全部净负**（恢复 1、打坏 9、净 −8） | 只要发生在 **FINAL 之后**，大概率越改越差。文档已判定「该方向可判定为已排除」 |
| **可选工具（递归）** | 调用率 12~15%，且两次运行「哪些题会调用」重合度只有 12~23% | **可选的东西不会稳定发生。** 想让它每题都做，就必须强制 |

由此定下三条设计红线：

1. **只问问题，不碰实现**——不出现 join / filter / group by / having 等字段
2. **必须在写 SQL 之前**——不是事后复核
3. **必须强制**——不是"你可以先分析一下"

## 三、具体设计

### 3.1 分析块的五个字段

字段是从根因表反推的，每一个都对应一类实测失败：

| 字段 | 问什么 | 对应机制 | 对应题 |
|---|---|---|---|
| `answer_shape` | 要返回几列、每列是什么 | 缺列 / 输出形状 | `bird_1529`、`bird_36`、`bird_26` |
| `counting_unit` | 数的是**实体**（人/卡/球员）还是**记录行**？ | 去重粒度 6 道 | `bird_1037`、`bird_1241`、`bird_1243` |
| `stated_conditions` | 逐条列出**题面里写死**的过滤条件 | 漏过滤 4 道 | `bird_48`（merged）、`bird_36`（rtype） |
| `unit_and_scale` | 百分比吗？要乘 100 吗？小数位？ | 少乘 100 3 道 | `bird_1149`、`bird_273`、`bird_263` |
| `ambiguities` | 题面**没说清**的地方 | 语义误读 3 道 | `bird_173`、`bird_1486` |

**五个字段全部是关于题目的,没有一个是关于 SQL 的**——这是与 E4-A 的关键区别。

### 3.2 时序

```
第 1 轮  ：模型只输出 ```question-analysis 块（五个字段），不许写 SQL
第 2 轮起：照常探索、写 SQL、FINAL
```

强制方式沿用 `query_plan.py` 已有的机制(检测到缺字段就退回要求补全)，
但**字段数从 20 降到 5，且全部是题意层面**。

### 3.3 落地方式（按项目惯例）

- 新 prompt profile `conventions-qa-v1`
- 新 `AgentConfig` 字段？**不加**——用已有的 `planner_mode` 加一个新取值
  `question-analysis-v1`，避免 `asdict()` 给所有 profile 增加键
  （`final_execution_gate` 那次就是这么把全部 sha 改掉的）
- 新 profile `e3-c-recursive-db-qa`，单变量对照 `e3-c-recursive-db`
- `__post_init__` 强制 `question-analysis-v1` 必须配 `conventions-qa-v1`

## 四、怎么测（分两阶段，先便宜的）

### 阶段一：46 道候选池，两臂对跑（约 30 分钟，先做这个）

**为什么可以只跑子集**：这个机制**每道题都会触发**（强制的），
不像递归那样随机落在 14% 上。所以在它该起作用的人群上做配对比较是有效的，
不存在「处理组分配不稳定」的问题。

- 臂 A：`e3-c-recursive-db`（基线）
- 臂 B：`e3-c-recursive-db-qa`
- 题集：`flatzero_23_root_causes` 的 46 道
- 每臂跑 2 次（这 46 道里有非单调型，单次不可靠）

**同时测两件事，缺一不可**：

1. **准确率**：46 道里翻对几道
2. **分析本身对不对**（机制检验，与最终答案无关）：
   - 6 道去重粒度题里，`counting_unit` 有几道正确写了"实体"？
   - `bird_48` 的 `stated_conditions` 有没有列出 merged？

第 2 项是关键——**如果分析本身就是错的，那准确率不管涨跌都不说明这条路的价值**。

### 阶段二：全量 498（约 3.2 小时/次，看阶段一结果再定）

只有阶段一同时满足才做：
- 准确率在 46 道上净正
- 分析正确率不低（否则先改分析设计，别急着跑全量）

全量至少 2 次，因为预期效应（+1~3pp）与噪声带（0.2~1.4pp）同量级。

## 五、顺带发现的另一条便宜路（与本计划独立）

根因表里**最大的单一类别不是理解问题，是类型/格式（11 道，24%）**——
模型算对了，输在返回值类型。其中 `bird_226/227/228/255` 是同一个子家族：

> 题面要求 "as a percentage with N decimal places"，模型用 `printf('%.Nf', ...)`,
> 在 SQLite 里返回 **TEXT**；gold 用 `ROUND(..., N)` 返回 **REAL**。
> 判分做元组比较，`'3.84615' != 3.84615`。

**这不需要模型更聪明，需要一条后处理规则**：`printf('%.Nf', x)` → `ROUND(x, N)`。
形状固定、可 AST 判定、与 `keep_ties` 同级别，**离线回放即可验证，零 API 成本**。

直接命中 4 道（+0.8pp），若把 `CAST` 那两道（`bird_1479`、`bird_931`）一并考虑还能更多。
**建议先做这条**——它比本计划便宜一个数量级，且两者不冲突。

## 六、风险

1. **最大风险是重蹈 E4-A**：任何"先想清楚再写"的强制结构都可能让模型变得僵化。
   E4-A 让它自己的目标类别变差了 4 道。缓解办法是字段只谈题意、不谈实现，
   但**这只是假设，阶段一就是用来证伪它的**。
2. **分析对了不等于 SQL 就对**。模型可能正确写出"要数病人不是数记录"，
   然后照样写 `COUNT(*)`。阶段一的第 2 项测量就是为了把这两件事分开。
3. **46 道是失败题构成的人群**，基线准确率本来就低，翻对容易翻错难，
   **子集上的增益会系统性高于全量**。阶段二不可省。
4. 类型/格式那 11 道在阶段一的人群里占 24%，**这条路对它们无效**，
   所以 46 道上的天花板实际是 31 道而不是 46 道。
