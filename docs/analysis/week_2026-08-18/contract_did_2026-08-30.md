# Answer Contract 的因果评估：契约有效，但不是靠字段（2026-08-30）

用反事实重采样评估「先写答案规格、再写 SQL」这个干预。数据
`analysisDetail/contract_did_2026-08-30.json`，样本
`analysisDetail/phaseA_resample/did_arm{A,B}_*.json`。

## 一、为什么不用准确率对比

Phase A 那 46 道上，**同一个臂两次重复能差 4 道**（08-26 的 gated 臂 11 vs 15）。
效应量级本身就是 ±2~4 道，聚合准确率分不出信号和噪声，再跑多少次都一样。

所以改成一个**可证伪的差异预测**。契约的每个字段对应一个具体失败机制，若它按声称的方式
起作用，提升应当集中在字段能命名的题上：

    DiD = [P(对|契约) − P(对|无契约)]_有字段 − [P(对|契约) − P(对|无契约)]_无字段

分组在跑之前冻结在 `analysisDetail/phase_a_mechanism_46.json`，24 道有对应字段、22 道没有，
每一类为何算 unmatched 也一并写明（口径取保守：「缺聚合」2 道算进无字段）。

## 二、两臂只差一件事

第一次起实验时两臂差了三件事（toolconfirm 保证、`recursive_llm` 说明、分析块），
DiD 会把前两件的效果算成契约的。**已作废重跑**，现在：

| | toolconfirm | recursive_llm | 分析块 |
|---|---|---|---|
| Arm A `conventions-recursive-toolconfirm-v1` | ✓ | ✓ | ✗ |
| Arm B `conventions-qa-toolconfirm-v1` | ✓ | ✓ | ✓ |

两个 prompt 是新加的（`prompts.py`），为的就是让两臂只差分析块。

## 三、结果

k=1、每题 N=10、`gpt-5.4-mini`、effort high。

| 组 | Arm A 无契约 | Arm B 有契约 | 差 |
|---|---|---|---:|
| 有对应字段（24 道） | 40/123 = 32.5% | 97/206 = 47.1% | **+14.6%** |
| 无对应字段（22 道） | 10/94 = 10.6% | 41/179 = 22.9% | **+12.3%** |
| 全部 | 50/217 = 23.0% | 138/385 = 35.8% | **+12.8%** |

**DiD = +2.3%**

**契约整体有效（+12.8pp），但不是通过命名要求起作用的。** 两组几乎同幅上涨，
DiD 远小于各自涨幅——这是「通用效果」的形状：**逼模型先把题读一遍再动手值 +12.8pp，
契约里具体写哪几个字段只多值 +2.3pp。**

据此**不再补** `numerator`/`denominator`/`source` 等字段，按 DiD 其边际接近零。

### 与 stage one 的 −3.3pp 对照

`question_analysis_stage1_2026-08-26.md` 测同一个干预是 **−3.3pp**，因为那批运行 46 道里
38 道没碰数据库（工具循环是死的，`dead_loop_root_cause_2026-08-30.md`）。分析块插进一个
单次生成器，只是多一段前言。**修好循环后同一干预变成 +12.8pp。**

这条对比本身是结论：**承诺前的干预要起作用，前提是 agent 真的在多轮工作。**

## 四、契约没有约束力，检查器才有

冒烟里看得最清楚：同一道题，模型在契约里写 `output_type: numeric`，转头用 `printf` 返回
字符串——**自相矛盾**，10 次里多次如此。契约让它「说了」，没让它「做到」。DiD 只有 +2.3%
正是同一现象的另一面。

新增 `ours/agent/contract_checks.py`，三条检查**全部读执行结果、不读 SQL 文本**——这是照着
`analysis_gate.py` 的教训定的，它的语法版误伤率 21.7~26.1%：

| 检查 | 触发条件 |
|---|---|
| `OUTPUT_TYPE` | 契约说 numeric，返回值是能转成数字的字符串 |
| `PERCENT_SCALE` | 契约说要 ×100，返回值落在 (0,1) 开区间 |
| `TIES_TRUNCATED` | 契约说保留全部并列，SQL 以 `LIMIT 1` 结尾，**且去掉 LIMIT 后实测多于一行** |

离线跑在 Arm B 自己的 385 个样本上，**不额外调用模型**：

| | |
|---|---|
| 触发 | 30 / 385 = **7.8%**（`OUTPUT_TYPE` 15、`PERCENT_SCALE` 15） |
| 机械修复 | **救回 13，打坏 0** |
| 无法机械修复 | 17（全是 `PERCENT_SCALE`） |

对照 `verify_before_limit` 的「恢复 1、打坏 9」，13/0 是本项目未出现过的比例。原因在设计：
检查只在**模型自相矛盾**时触发，不需要判断题意，所以不误伤。

`TIES_TRUNCATED` 一次未触发——这批题的 `tie_policy` 基本是 `n/a`。**本池子测不出它，
不在此下结论。**

### 一个自己造的 bug，值得记

第一版报「救回 0」。原因是修复正则用了非贪婪匹配，在**第一个右括号**截断：

    原  : printf('%.5f', CAST(SUM(CASE ... END) AS REAL) * 100.0 / COUNT(bond_id))
    错修: ROUND(CAST(SUM(CASE ... END, 5) AS REAL) * 100.0 / COUNT(bond_id))
                                  ↑ 参数插进了 SUM 里面

**语法能跑、结果错、静默失败。** 改成括号配平后同样的样本救回 13。
`printf_to_round` 现在只有一份实现（在 `contract_checks.py`），agent 与离线评分共用，
防止两份实现漂移。

## 五、Verifier 的分母算得出来了：17 个样本

那 17 个 `PERCENT_SCALE` 有确凿证据（契约说要 ×100、结果在 (0,1)），但**没有安全的机械
修复**——×100 该乘在表达式哪一层取决于表达式本身，这正是本项目历史上误伤的来源。

**这是架构里唯一还值得建 Verifier 的地方，触发率 4.4%（17/385）**，符合「verifier 只在
少量高风险题上触发」。建之前应按 matched-call control 设计测一次。

## 六、边界

1. **两臂有效样本数不同**：Arm A 217/460（47%），Arm B 385/460（84%）。无契约那臂大量样本
   卡在「没交出干净 FINAL」。两臂比较的不是同一批样本，Arm A 的 23.0% 受选择效应影响；
   DiD 对此部分免疫（两组共享同样偏差），但不完全。
2. **13 个 rescue 集中在 3 道题**（`bird_226/227/228`，同一个 printf 家族），**不是 13 道
   独立的题**，不能按题数外推。
3. **13/0 不能外推到真实 agent——已实测，见下节。**
4. **循环健康度已核实，不再是限制**：Arm A 第 1 轮带代码 **99%**，健康期（08-17）是 93.9%、
   源 trace（08-22）95.8%、死循环期 0%。此前担心的「不能外推到健康 agent」不成立。
   （Arm B 该指标不可比：QA 协议规定第一轮就是分析块。）

## 七、检查器在真实 agent 上的双臂对照：触发 0/92，方案作废（2026-08-31）

离线的 13/0 是在 k=1 重采样上测的。把同一条检查放进完整 agent 循环，在同一批 46 道上
跑双臂、各两次重复：

| 臂 | run1 | run2 | 均值 |
|---|---:|---:|---:|
| `e3-c-recursive-db-qa-live`（无检查） | 14/46 | 13/46 | **13.5** |
| `e3-c-recursive-db-qa-checks-live`（+检查） | 12/46 | 14/46 | **13.0** |

两个 profile 逐字段比对只差 `contract_checks` 一个布尔值。

**检查器触发 0/92 次，改写 0 次。** 两臂的差异不含任何检查器的作用，全部是采样噪声——
同臂重复（`qa-live` run1 vs run2）逐题翻转 **11/46**，跨臂（run1 两个 profile）翻转
**12/46**，跨臂差异落在同臂噪声之内。

### 为什么离线 3.9% 的触发率到真实 agent 变成 0%

| | k=1 重采样 | 真实 agent |
|---|---:|---:|
| `OUTPUT_TYPE` 触发率 | 15/385 = 3.9% | **0/92 = 0%** |

真实 agent 有 8 轮循环，能执行查询、看到返回值、自己把 `printf` 改回 `ROUND`；k=1 只生成
一轮，模型没有这个机会。**那 13 个 rescue 修的是只在单轮重采样里才存在的错误。**

### 方法学教训：k=1 的样本分布不等于真实 agent 的样本分布

反事实重采样是有效的**诊断**工具——本文第三节的 DiD 结论不受影响，因为那是两臂共用同一套
k=1 方法做的**相对**比较，两边共享同样的分布偏差。

但它不能用来估计一个干预的**绝对**收益：在 k=1 上测出的「可修复错误」，可能是真实 agent
本来就会自己修掉的。**任何干预的收益必须在完整 agent 上复测。**

这与本项目已有的几条教训同源（机械判定被证伪四次、事后复核五次净负），但角度是新的：
前几次错在**判据**，这次错在**测量的人群**。

### 处置

`contract_checks` 保留代码、默认关闭（`False`），`e3-c-recursive-db-qa-checks-live` 保留
为消融记录。检查逻辑本身没有缺陷——零误报、修复正确、单测通过——它只是**在真实 agent 上
没有作用域**。

### 顺带一个信号

真实 agent 上契约臂是 13.5/46 ≈ **29%**，与 k=1 上 Arm B 的 35.8% 同量级，而 k=1 的
Arm A 只有 23%。这提示**契约的收益在真实多轮 agent 上可能已被循环本身吃掉一部分**——
多轮执行反馈和「先读题」在功能上有重叠。

这 46 道是筛出来的最难一批，机制在这里测不出效果是意料之中。**下一个该回答的问题是
「契约在完整 498 道上值多少」，而不是继续在这 46 道上加机制。**
