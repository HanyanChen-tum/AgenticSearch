### 1.3 ❌ **更正**：「75% 的题一轮交卷」不成立

| profile | 一轮率 | 多步率 | `db.execute` 次数 |

### 1.4 ⚠️ 新发现的缺陷：模型响应格式在两轮之间发生漂移

追查 1.3 的异常，读 `keepties` 轮的原始消息：

```
[assistant] SELECT COUNT(*) FROM client AS c INNER JOIN ...     ← 裸 SQL，没有 ```python 包裹
[user]      REPL Error: SyntaxError: Invalid star expression
[assistant] FINAL("SELECT COUNT(1) FROM ...")
```

模型输出**裸 SQL 而不是 ```python 代码块**，REPL 按 Python 解析必然报错，
于是一次库都没查成。统计：

| 运行 | 裸 SQL 回复 | ```python 块回复 | REPL 报错 |
|---|---:|---:|---:|
| `recursive_db` run1（基线） | 59 | **539** | 64 |
| `keepties` run1 | 88 | **3** | 90 |
| `final_gate` run1 | 90 | **7** | 91 |

**排除的可能性**（都已核实）：
- 不是 prompt 改动：三者 `prompt` sha 均为 `9b605cf1bd72e74a`，与当前代码一致
- 不是配置差异：`max_iterations=8`、`effort=high`、`capability_gate=True`、
  `allowed_db_methods` 完全相同
- 不是我的 profile 引入：`keepties` 与基线唯一差别是 `sql_convention_mode`，
  一个**后处理**开关，不进 prompt、不改工具

**剩下的解释是模型侧行为漂移**（同一部署、不同时间，响应格式偏好变了）。

**这条的影响很大**：
1. `keepties` 全量那轮的 +0.23pp **是在一个工具循环实际失效的状态下测的**，
   与基线不可比 —— 之前记录的"全集 +0.23pp"必须作废重跑
2. 它同时解释了 `final_gate` 全量那轮 87.50% 偏低
3. **任何跨时间的运行对比都需要先检查这个指标**

### 1.5 ✅ 成立但需重新理解：递归调用不稳定

同配置两次运行，"哪些题调用了递归"的 Jaccard 重合度 11.8% / 23.2%。
结合 1.4，这**可能部分也是响应格式漂移**造成的，而非纯采样随机。**待验证。**

### 1.6 ✅ 成立：实验人群必须按机制目标类选

## 二、框架的核心主张

> **grammar 的载体应该是「模型输出与正确答案的系统性差异」，不是 reasoning trace。**

对比两种载体（依据第一节的核实结果）：

| | trace grammar | 差异 grammar |
|---|---|---|
| 输入 | 模型怎么想的 | 模型写了什么 vs 该写什么 |
| 稳定性 | 低（调用重合度 12~23%，且受 1.4 的格式漂移干扰） | **高**（同一变换在 5 个运行上代价恒为 2 道） |
| 是否需要模型配合 | 需要 | **不需要，确定性执行** |
| 已有实测 | 三次尝试全阴（1.2） | 两条全阳（1.1） |

这不否定 trace 分析的价值——**反事实重采样正是我们用来做因果验证的工具**。
区别在于：trace 用来**发现和验证**，grammar 的**产物**是可执行变换。

## 三、三层结构

```
第 1 层  挖掘   从 (模型 SQL, gold SQL) 对里自动抽取候选 AST 变换
第 2 层  验证   每条候选做反事实：全集施加 → 重新判分 → 救回/打坏
第 3 层  上线   通过阈值的成为可消融规则，配 profile 开关
```

**第 2 层是关键,也是本项目已经跑通的部分。** `keep_ties` 和 `printf_to_round`
就是人工完成第 1 层、自动完成第 2、3 层的产物。框架要做的是**把第 1 层也自动化**。

### 3.1 第一层：候选变换的挖掘

输入是已有的 498×N 个 `(predicted_sql, gold_sql, correct)` 三元组。
对每个**判错**的样本，计算两棵 AST 的差异，归约成「变换模板」：

```
bird_671:  ORDER BY b.Date ASC LIMIT 1   →   WHERE b.Date = (SELECT MIN(...))
bird_794:  ORDER BY ha.value DESC LIMIT 1 →  WHERE ha.value = (SELECT MAX(...))
                                    ↓ 归约
模板：  ORDER BY <k> <dir> LIMIT 1  →  WHERE <k> = (SELECT MAX|MIN(k) FROM <同行集>)
```

**归约必须丢弃具体列名和表名**，否则得到的是记忆而不是语法。
一个模板只有在**跨库、跨题**出现多次时才成为候选。

### 3.2 第二层：因果验证（沿用本周已验证的方法）

每条候选模板：

1. 在**全集 498** 上施加，不只在失败题上 —— 1.6 的教训
2. 执行改写后 SQL，用 `is_correct` 重新判分
3. 报**两个口径**：靶子人群命中率、全集净值
4. 代价必须逐题可查（哪几道、为什么）

**阈值**（依据 1.1 的实测分布）：净值 > 0 且代价在多个运行上稳定。

### 3.3 第三层：上线

沿用 `sql_conventions.py` 已有机制：规则进 `_RULES`，
artifact 里带 `enabled` 开关，新 profile 单变量对照。

## 四、这个框架的可迁移性

三条与 BIRD 无关：

| | 依赖什么 | 换个数据集还成立吗 |
|---|---|---|
| `keep_ties` | 「最值查询」+「集合判分」 | ✅ 任何 text-to-SQL 评测 |
| `printf_to_round` | SQLite 的 `printf` 返回 TEXT | ✅ 任何用 SQLite 的场景 |
| 挖掘+验证流程 | 有 `(输出, 正确答案)` 对 | ✅ **任何可自动判分的生成任务** |

**第三条才是 framework**——它不要求任务是 SQL，只要求输出可结构化比较、结果可自动判分。

## 五、关于 offload 给小模型

有实测支撑，但形态与直觉不同：

- 四档推理强度实测：`minimal` 72.2% → `high` 87.0%
- **「能查库但几乎不想」(72.2%) ≈「使劲想但只能答一次」(70.5%)** ——
  工具循环与内部推理在很大程度上是**替代品**
- 推理量↓则工具调用↑（2.27 → 3.34），是替代关系的直接证据

所以「大模型找 pattern、小模型执行」的可行形态是：

> 大模型的产物**不是自然语言 pattern**（那正是 1.2 三次失败的东西——模型不照自己的话做），
> 而是**可执行规则**。小模型只负责生成，规则在提交时确定性修正。

**可直接测**：低 effort 臂 × 开启两条规则，对比 high effort。零新代码，只是新 profile。
**但必须等 1.4 那个格式漂移问题查清楚**，否则跨时间对比不可信。

## 六、动手顺序

1. **先修 1.4** —— 在此之前所有新跑的全量都不可信。至少要能检测：
   在 runner 里统计 ```python 块比例，异常时告警

3. **实现第一层挖掘脚本** —— 用已有 5 个运行的数据，看能否自动挖出
   `keep_ties` 和 `printf_to_round`（**它们是这个框架的验证集**：
   挖不出来说明挖掘方法不行）
4. 挖出新候选后走第二层验证

**第 3 步是这个框架成不成立的判据**：如果自动挖掘能重新发现两条已知有效规则，
它就有理由去找未知的；如果挖不出来，说明第一层的设计还不对。

## 七、风险与边界

1. **最大风险是挖出「记忆」而不是「语法」**。若模板保留了具体列名，
   它只在这个数据集上有效。归约的激进程度需要实验确定。
2. **本文第一节 1.4 是新发现的缺陷，尚未修复**，它可能影响 1.5 甚至更早的一些结论。
3. **第五节的 offload 假设完全未测。**
4. 三条"可迁移"的论断是分析判断，**没有在第二个数据集上验证过**。
