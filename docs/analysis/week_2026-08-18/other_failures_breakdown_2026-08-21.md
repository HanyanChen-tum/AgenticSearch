# 拆开「其它」424 道失败（2026-08-21）

`WEEK_PLAN_2026-08-20.md` §二排的任务：把五层链失败集里最大的一类——「其它」
（不属于约定类、不属于行集类的 424 道）——再拆开一层。做法延续项目的既有约束：
只用可重执行验证的事实，不用另一个模型贴标签。

---

## 一、新增两条可复算检查

[`scripts/triage_failure_causes.py`](../../../scripts/triage_failure_causes.py) 原有三条
（`ties`/`under_projection`/`distinct_repair`），本轮加两条，都是纯数据变换、不需要重新执行 SQL：

| 检查 | 命中条件 |
|---|---|
| `column_permutation` | gold 与模型返回的行、列完全相同，只是列顺序不同（枚举到 5 列） |
| `concat_columns` | gold 是多列，模型把它们拼接成了一列字符串（如 `forename, surname` → `"forename surname"`） |

顺带修了一个 bug：`_as_multiset` 直接 `sorted()`，遇到同一列里 `None` 和字符串混排会抛
`TypeError`（`clean_e0_run2` 触发过一次）。改用 `shared/evaluator.py` 里 `normalize_answer`
同款的字符串强制转换排序键，八个臂全部重跑，无新崩溃。

**效果**：约定类相关命中从 91 道涨到 110 道（+19），覆盖率从 16.6% 涨到 20.0%。

## 二、但这两条新检查不是「约定类」的同类——推理量证据

分开看四类失败的推理量（八臂合并，剔除 harness 崩溃）：

| 类别 | n | 推理量中位 | 相对答对 |
|---|---:|---:|---:|
| 答对 | 3414 | 2036 | 1.00× |
| **自信型失误**（`ties`/`under_projection`/`distinct_repair`，即原「约定类」三条） | 91 | **1619** | **0.79×** |
| **格式型失误**（新两条：`column_permutation`/`concat_columns`） | 19 | **3956** | **1.94×** |
| 行集类 | 34 | 4434 | 2.18× |
| `no_answer`（harness 崩溃，已从统计里剔除，仅列出对照） | 21 | 3627 | 1.78× |
| 其它（仍未解释） | 384 | 4237 | 2.08× |

**新两条检查命中的失败，推理量几乎是答对题的 2 倍，跟「自信型失误」的 0.79× 方向相反。**
如果把它们并进原来的「约定类」（本轮一开始就是这么做的），约定类整体的推理量中位数会从
1619 涨到 2022，冲淡"模型不知道自己错了"这条结论的信噪比。**拆开后原结论完整保留、
范围更精确**：真正「一次成型、自信但错」的只有 `ties`/`under_projection`/`distinct_repair`
这三条，列顺序错位和姓名拼接是模型**想了很久之后**仍然选错格式，属于另一种失败模式——
更接近真实难度带来的失败，只是表现形式恰好是格式不对。

[`five_layer_chain_results_2026-08-19.md`](five_layer_chain_results_2026-08-19.md) §三的
「约定类」结论建立在原三条检查上，**结论不受影响**，但引用时口径要收窄为这三条，
不能扩展到本文新增的两条。

## 三、量化了一个大的子模式，但没有机械化——比例/分子分母公式

对 107 道去重后的「其它」失败做正则扫描（gold 含 `CAST(...AS REAL)/`、`SUM(...)/(COUNT|SUM)`
等比例公式形状，pred 也含除号）：

**30/107（约 28%）疑似是比例公式分子分母选择不同**。抽样读了 15 道，形状一致：

```
gold: CAST(SUM(CASE WHEN cond THEN 1 ELSE 0 END) AS REAL) / SUM(CASE WHEN cond2 THEN 1 ELSE 0 END)
pred: SUM(CASE WHEN cond THEN 1 ELSE 0 END) * 1.0 / COUNT(*)
```

分子往往一致，分母不一致——是该用「满足另一条件的行数」还是「全部行数」，
是「按人去重计数」还是「按记录计数」。

**没有为此写机械修复检查**，理由是这类问题的正确修法需要理解题意——哪个分母是题目真正要的，
不是通用的 SQL 语法变换。这跟已经被证明有害、因而关掉的 `count_no_distinct` 后处理规则
（[`sql_postprocessing_rules_2026-08-16.md`](../sql_postprocessing_rules_2026-08-16.md)）是
同一类风险：那条规则的 disabled 理由写的是「改变了 COUNT 在数什么」，不是「改格式」。
硬造一个「试几种替换，撞上算命中」的检查，本质是在猜，属于本项目已经证伪过四次的
机械判定的同一种错误，不能再犯一次。

**这不是没有进展**——把「其它」里 28% 定位到一个具体、有名字的子模式，
比继续统称「未解释」更接近可以人工判读的状态，只是判读工作量本身没法省。

## 四、覆盖率现状

| 类别 | n | 占比 |
|---|---:|---:|
| 自信型失误（原约定类三条） | 91 | 16.6% |
| 格式型失误（新两条） | 19 | 3.5% |
| 行集类 | 34 | 6.2% |
| `no_answer` | 21 | 3.8% |
| 比例公式（已定位，未机械化） | ~30（`other` 384 的子集，未去重到臂级） | ~5.5%（占总失败） |
| 其它（仍完全未分类） | 384（含上面的比例公式子集） | 69.9% |

可复算检查总覆盖率约 30%（91+19+34+21=165/549），与 `WEEK_PLAN` 预判的
「若覆盖率仍只有 30~40%，其它就只能作为混合类报」基本吻合。**没有达到能做统计的水平，
不建议把「其它」当作单一类别做进一步的定量分析**，下一步只能是人工判读，
而不是继续加机械检查——比例公式那 30 道已经是本轮能安全找到的最后一块大子模式。
