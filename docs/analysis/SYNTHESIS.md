# 项目综合结论：冻结商用模型上 系统侧干预的结构性天花板

版本：2026-08-08
适用范围：本文档综合 E0–E5 全部已完成实验、两轮 F-Audit、分类器修复、ReAct 循环有效性测量和标注约定挖掘，给出可对外表述的核心论点、证据链和边界条件。它不替代 `README.md`（实验流水记录）和 `../experiment-plan/README.md`（协议与计划），而是把分散结论收敛成一个论证。

## 0. 四条主要结论（摘要）

本项目最终产出四条相互独立、各自成立的结论。原定的 RLM 三能力验证没有得到正面结果，但下列四条都需要本项目建立的 error tracking 基础设施才能得出。

### 结论一：一个有效机制（E3-C Offline Schema Context，+4.82 pp）

把逐题注入的**全量数据库 Schema**替换为**按题确定性检索的相关片段**（表/字段描述、PK/FK 图、join 边的 cardinality 与 fan-out、值格式），未选中的表只给 names-only 索引。

- 结果：`77/197 = 39.09%`，相对 E0 两次均值 `34.26%` 提升 **+4.82 pp**（9.5 题）
- 该效应量高于后来实测的同配置重跑方差 6 题（§4.4），因此结论在方差修正后依然成立
- 这是六个受测的**模型侧**机制中唯一被接受的；后来另有一个**系统侧**机制被接受，见结论四
- 代价：total tokens/题 +14.29%，因此只能称"准确率有效"，不能称"效率改进"
- 详见 §2.3 与 `analysisDetail/e3_c_schema_v4_summary.md`

### 结论四：第二个有效机制，且它划出了有效与无效的分界（标注约定后处理，+5 题）

从 train 挖出三条 BIRD 书写约定（分列不拼接 99.99%、最值用 `ORDER BY...LIMIT` 90.34%、计数遇 JOIN 不去重 89.10%），**由 harness 对最终 SQL 做确定性改写**，两次独立测量净收益均为 **+5 题**。

真正的价值不在这 5 题，而在同一批约定的**两种交付方式**构成了受控对照：

| 交付方式                                       | 效果                               |
| ---------------------------------------------- | ---------------------------------- |
| 写进 Prompt（E3-A 静态 patterns 逐字含此内容） | **0**——违反计数 24 vs 25   |
| 由 后处理确定性改写                          | **+5**，且模型跑好跑坏都复现 |

这是本项目反复出现规律的最干净一例：**系统侧确定性干预可复现，模型侧干预被噪声淹没。**
性质须如实说明为**标注对齐**而非 SQL 能力提升——转正题中含 F-Audit 判定的 gold 缺陷题。
详见 `rootcause/convention_postprocessing_2026-08-08.md`。

### 结论二：一个结构性负面结论（验证类干预的天花板）

**在冻结的商用模型上，任何"让模型多验证一步"的干预都会失败，因为失败在验证能够介入之前就已经决定。**

- 四个独立设计的验证类机制全部失败或归零：E1 strict verified-final、E4-A QueryPlan、字面量核实提醒、JOIN 精简提示
- 根因由 ReAct 循环实测给出：失败题的 wrong→correct 恢复次数**三次运行精确为 0**，且 **99% 以上的失败题全程从未执行出匹配 gold 的结果**——循环没有可救的对象；模型也不会在将要出错时增加探索（正确题与错误题的执行次数几乎相同）
- **这一条不可读作"ReAct 无用"。** `../findings.md` 记录 ReAct loop + live DB tools 为 **+9.0**，是本项目最大单项增益之一。两者的区分是**时序**：ReAct 作为**承诺之前的落地取证**有效（+9.0），作为**答案已有之后的挽救**无效（恢复率 0；同表中 `Post-answer verification prompt` fixed 0 / broke 3、`Blocking FINAL until exploration` fixed 0 / broke 8）。所有验证类机制的失败都属于后者。E6 实验进一步证实：即使把"取证"做成确定性机械测量再喂回，只要发生在答案已有之后，仍与纯重试无差别（§6.2）
- 这不是四次独立的设计失误，是同一个结构性原因
- 详见 §2.1–2.2 与 `analysisDetail/react_loop_efficacy_2026-08-08.md`

### 结论三：一个基准质量发现（可测 headroom 被显著高估）

**BIRD 困难子集上看起来存在的提升空间，有相当一部分并非模型能力不足，而是标准答案本身的问题。**

三条独立证据指向同一结论：

0. **对"稳定能力缺陷"子集的逐题审计（最强的一条）**：在最应当代表真实能力差距的 77 条（六配置全败、且已被机械检测器排除已知 gold 缺陷）中分层抽样 31 条逐题判定，结果**仅约 10% 是模型真实推理错误**；32% 是可执行验证的 gold 缺陷（如 gold 用 `ASC` 回答"最高"、对 text 类型列做字符串排序取最大值），42% 是数据集未指定输出约定（返回 id 还是 name）或指代歧义（两表同名列）。详见 `rootcause/stable_failure_audit_2026-08-08.md`。

0c. **第二个干预性验证：Hint 本身是致败原因之一**。BIRD 的 `evidence` 字段在一个可机械识别的子集上（Hint 声明的公式与 gold 实际实现不符，197 题中命中 29）**主动致败**：三臂消融显示，删除 Hint 后该类原本失败的题 **0/5 → 3/5**，同时对照组（同签名但原本正确 5 题、值编码型 Hint 原本正确 5 题）**均无任何损害**。机制清楚——`bird_604` 的 Hint 写 `Divide(Sum(UpVotes), Count(UserId))`，模型照做写出 `SUM/COUNT`，gold 却用 `AVG`；删掉 Hint 后模型自行写出 `AVG` 并与 gold 一致。**模型因忠实执行给定指令而被判错。** 值编码组无损害提示 E3-C 的 Schema artifact 已携带 `value_description`，使 Hint 冗余——这与 `findings.md` 中 legacy 时代"Hint 为 large positive"的记录不矛盾，因为那是在没有 Offline Schema Context 的 harness 上测的。详见 `rootcause/hint_ablation_2026-08-08.md`。

0b. **干预性验证（不再只是观测）**：对上述"指代歧义"一类做反事实实验——只改写问题中那一个歧义名词（不出现表名/列名、不透露输出结构），其余全部不变。**命中预期指代对象从 1/7 升至 6/7**，证明模型并非选不对表，而是**题面未提供选择所需的信息**；整题转正 0/7 → 2/7，其余在指代纠正后撞上同一题并存的其它数据集侧问题（DISTINCT 约定、输出约定、空值约定）。这把结论三从观测性证据提升为**干预性证据**。详见 `rootcause/disambiguation_experiment_2026-08-08.md`。

1. **F-Audit（逐题执行验证）**：20 题样本中 **40% 的"失败"是 gold 本身有缺陷**，仅 30% 是干净的 Agent 错误。其中"缺 DISTINCT"跨 4 个数据库反复出现。
2. **标注约定量化**：train 与 eval 中"计数+JOIN"场景约 85% 的 gold 不使用 `COUNT(DISTINCT)`；模型系统性违反且方向完全一致（9/9 全是"模型去重、gold 不去重"，反向 0 例）——**模型写出的是语义上更正确的 SQL 却被判错**。机械对齐该约定即可换取 **+2.03 pp**，与查询能力无关。

含义：**在此类基准上报告的机制收益，必须先扣除数据集缺陷与标注对齐的部分**，否则会把"学会模仿标注习惯"误报为"提升了 Text-to-SQL 能力"。

- 详见 §4 与 `analysisDetail/filter_audit.md`、`analysisDetail/annotation_convention_mining_2026-08-08.md`

## 1. 核心论点

> **在冻结的商用 LLM 上，"验证类" 系统侧干预存在结构性天花板：失败在验证环节能够介入之前就已经决定。**

三个可独立验证的子命题：

- **S1（失败早决）**：失败在第一次数据库执行时就已确定，多轮循环无法挽回。
- **S2（验证无效）**：所有强化"自我检查/验证"的机制都会失败，且这不是设计问题，是 S1 的必然推论。
- **S3（信息有效）**：唯一奏效的干预类型是改变模型**看到什么**，而非告诉模型**怎么做**。

## 2. 证据链

### 2.1 支持 S1：失败早决

| 证据                                           | 数值                              | 来源                                  |
| ---------------------------------------------- | --------------------------------- | ------------------------------------- |
| 失败题在首次`db.execute` 即偏离              | 81–106 / 120–126                | 各 trajectory audit                   |
| 失败题**全程从未**执行出匹配 gold 的结果 | 119/120（E3-C）、127/128、129/131 | `react_loop_efficacy_2026-08-08.md` |
| 失败题 wrong→correct 恢复次数                 | **0 / 0 / 0**（三次运行）   | 同上                                  |
| E4-A 中"计划被忠实执行但计划本身错误"          | 82 / 126                          | `e4_a_core197_run1_summary.md`      |

失败题不是"接近正确但循环没抓住"，是从未接近过正确答案。这是 S1 最强的单条证据：**循环没有可救的对象**。

### 2.1.1 剥离数据集问题后，剩余失败对整类干预免疫

对 E3-C 的 120 条失败做机械分解并用四个检测器剥离 gold 缺陷后（`analysisDetail/failure_decomposition_2026-08-08.md`，对 F-Audit 8 条人工验证缺陷召回 8/8）：

| 项                             |                                 数值 |
| ------------------------------ | -----------------------------------: |
| 机械可确证的数据集问题         | 9–13 条（另约 10 条疑似待人工验证） |
| 未被标记的候选真实错误         |                                88 条 |
| 其中**六个配置全部答错** |             **77 条（87.5%）** |
| 其中至少一个配置解对过         |                       11 条（12.5%） |

六个配置涵盖不同 Prompt、不同知识注入、有无 QueryPlan、有无 Schema 检索。**77/120 = 64% 的失败对这一整类 系统侧干预免疫**——这不是"还没找到对的 Prompt"，是六次独立配置的交叉验证结果。

> **免疫的原因经逐题审计后已查明，与最初推测不同**（`rootcause/stable_failure_audit_2026-08-08.md`，抽样 31 条、关键判定经执行验证）：这 77 条中仅约 **10%** 是模型真实推理错误，**32%** 是可执行验证的 gold 缺陷，**42%** 是数据集未指定输出约定或存在指代歧义。因此"免疫"不是因为模型能力不足到无法改进，而是**这些题目的正确答案本身无法从题面推导**——再好的 harness 也猜不中未声明的输出约定，更无法复现 gold 的缺陷。

最大失败类别的内部结构进一步说明性质：39 条是单数字答案，其中 **24 条差 2 倍以上或不足一半**（数量级偏差，非边界/舍入问题），**整数倍 0 条**（否定了"JOIN 行膨胀导致计数放大"这一常见假设）。模型不是算错某一步，而是**从一开始就在计算另一个量**。

### 2.2 支持 S2：验证类机制全部失败

| 机制                             | 干预方式                                       | 结果                                                         |
| -------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| E1 strict verified-final         | 强制 FINAL 必须等于最近成功执行的 SQL          | 拒绝：调用/token 翻倍，稳定失败恢复 0，稳定正确退化 3        |
| E4-A QueryPlan + Output Contract | 强制在生成 SQL 前输出结构化计划                | 拒绝：71/197，较父配置 −6 题；目标类别（聚合/排序）反而变差 |
| 字面量核实提醒                   | 未经`sample_values` 核实的字面量比较时软提示 | 拒绝：N=44 分层验证，0 恢复 / 4 回退                         |
| JOIN 精简提示                    | 协议中加入"只连必需表"规则                     | 暂停：N=26 v1 净 +1、v2 净 0；发现样本内"脆弱题"噪声         |

四次独立设计、独立测试，全部失败或归零。**共同点是它们都在强化 SC（自我检查）环节**，而 §2.1 显示该环节对失败题的边际价值≈0。

补充证据（模型不会自适应探索）：

| 指标                 |  正确题 |  错误题 |
| -------------------- | ------: | ------: |
| 执行次数/题（E3-C）  |    1.22 |    1.38 |
| 多次执行占比（E3-C） |   27.3% |   30.0% |
| 8 轮迭代预算实际使用 | 1–2 轮 | 1–2 轮 |

模型在即将答错时的探索强度与答对时无差别——它不知道自己不知道。这解释了为什么"提醒它去检查"无效：问题不在于提醒不够，而在于它无法判断何时需要检查。

### 2.3 支持 S3：信息类干预有效

| 干预                        | 类型                                                   | 结果                                          |
| --------------------------- | ------------------------------------------------------ | --------------------------------------------- |
| E3-C Offline Schema Context | 改变交付给模型的信息（用检索片段替代全量 Schema 注入） | **接受：39.09%，相对 E0 均值 +4.82 pp** |
| E3-A static patterns        | 往 Prompt 注入静态规则内容                             | 弱（+2.79 pp），不作为父配置                  |
| E3-B patterns 替代 few-shot | 移除信息                                               | 拒绝                                          |
| E3-D Query Mining           | 从 train question n-gram 挖掘 SQL 结构规则             | 不可行：0/28 slot 通过跨库门禁                |

**信息类干预内部还有一条更细的分界。** E3-C 成功而 E3-D 失败，差别在于所供信息是否为模型可自行获得：

- E3-C 提供**模型无法从问题文本推断的数据库事实**（表结构、字段语义、PK/FK 路径）→ 有效。
- E3-D 试图提供**模型已能自行推断的结构判断**（从问题表述预测输出列数、是否 LIMIT、是否 ORDER BY）→ 无效。实测最佳 slot `output_count` 精度 0.906，而模型自身在同一判断上的准确率是 **0.891**——规则仅强 1.5 pp，按 40.9% 覆盖率折算期望收益约 +0.6 pp（197 题上约 1 道），**低于本项目实测的 Prompt 扰动噪声（±4 道）**。详见 `analysisDetail/e3_d_query_mining_diagnosis_2026-08-08.md`。

由此得到 S3 的加强表述：**信息类干预的收益取决于所供信息是否为模型不可自行获得的；重复模型已有能力的信息不产生收益，无论其统计验证多严格。**

六个机制中唯一被接受的是 E3-C，且它属于"改变信息组织与交付"，不属于"指令模型行为"。

| -------------------------- | -----------------------------: |
| E0 run1 / run2             | 35.03% / 33.50%（均值 34.26%） |
| E3-A                       |                         37.06% |
| E3-B                       |                         36.55% |
| **E3-C（当前最佳）** |               **39.09%** |

## 2.4 三个 RLM 能力各自的结论

项目的三个目标能力现在各有一个**有原则的**结论，而不是"没来得及做"：

| 能力                                   | 对应实验                         | 结论                                     | 依据                                                                                                                                                                                                                                                                                    |
| -------------------------------------- | -------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **一：可编程上下文与代码化推理** | E5-A（通过）、E5-B（不建议运行） | **该能力针对的约束在本任务不存在** | 完整知识载荷 726–2,572 tokens，prompt 约 5,171 tokens，**上下文利用率约 4%**。context store 解决"上下文装不下"的问题；此处无此问题，外部化只剩开销：+109% token、+312% 延迟、准确率持平（N=11）。且 E3-C 残留失败中 89–93% 的所需信息**本已在上下文中**——查找不是瓶颈。 |
| **二：受控执行环境**             | E2-A、E2-B（完成）               | **有效但按定义不产生准确率收益**   | 计划原文即写明"不作为准确率机制"。E2-B 实测中性。其价值是让实验可归因（本项目分类器修复的经历直接证明了这一点）。                                                                                                                                                                       |
| **三：自我改进与分而治之**       | E4-A（拒绝）、E6（有原则暂缓）   | **前提不成立**                     | QueryPlan 使目标类别变差；递归要求模型可靠判断"哪个子计划需独立验证"，而模型在失败题上恢复率精确为 0、且不会在将要出错时增加探索（§2.2）。触发依据不成立时 Leaf 无法被公平评估。                                                                                                       |

**合起来是一个完整的负面结论**：RLM 的三个能力在 BIRD Text-to-SQL 这一任务、这一规模上都不产生预期收益，且每一条都有具体的结构性原因（约束不存在 / 定义上不提分 / 前提不成立），而非实现不到位或预算不足。

## 3. 与外部工作的关系

### 3.1 SQRL（usefeyn.com，BIRD Dev 70.6%）

SQRL 的**推理时架构与本项目基本等价**：只读探查数据库、值 grounding、多轮 observation 反馈、探查次数上限。差异在于它用 execution-based RL（CISPO）在"mixed zone"（8 条轨迹部分成功的题）上训练模型，学习**哪些 inspection 决策区分了对错**。

这对本项目的意义是双向的：

- **解释力**：它说明"何时该探查、探查什么"是训练习得的能力。本项目四次指令类干预的失败因此不是偶然，而是可预期的。
- **对照价值**：同架构 + 训练 = 突破天花板；同架构 + 仅指令 = 天花板。本项目正好是这个对照的另一半。

需要注意的边界：SQRL 是**领域专用模型**（BIRD/Spider 上训练），本项目的前提是"不换更大或领域专用的模型"。因此不能把 SQRL 方案直接移植，两者回答的是不同问题。

### 3.2 Thought Anchors（Bogdan et al. 2025）

该工作提出推理步骤分类（PS 问题设置 / PG 计划生成 / FR 事实检索 / AC 主动计算 / UM 不确定性管理 / SC 自我检查 / RC 结果合并 / FAE 最终答案）与反事实重采样归因方法，发现 planning 类步骤影响力不成比例地大，computation 类相对可替换。

本项目在**动作层独立复现了这一结论**：PS/PG 阶段（首次执行之前）决定成败，SC 阶段因果影响≈0。

方法论限制：本项目使用 `azure/seminar-gpt-5.4-mini`，reasoning token 仅计费不返回内容（E3-C 实测 7,836 reasoning tokens/题，约占 completion token 的 93%）。因此**句子级 CoT 分析在本 setup 下无法进行**，只能做动作层的粗粒度对应。

## 4. 第二条独立结论：测量工具与数据集质量

除主论点外，本项目产出了一条关于**评测本身可信度**的结论，它独立成立且影响所有基于 BIRD 困难子集的工作。

### 4.1 自动分类器存在系统性漏检（已修复）

原分类器仅检查 SQL 关键字**是否出现**，不比较具体内容：GROUP BY 的分组字段、ORDER BY 的排序字段、JOIN 的连接键、LIMIT 数值均未比较。修复后重新生成全部 8 个已完成实验的分类，结果：

| 语义类别（E0 两次合计 259 条失败） |             修复前 |                       修复后 |
| ---------------------------------- | -----------------: | ---------------------------: |
| Schema/Join                        | 38（14.67%，最小） | **97（37.45%，最大）** |
| 聚合与排序                         | 93（35.91%，最大） |                 65（25.10%） |
| 输出契约                           |                 56 |                   56（不变） |
| 过滤/低置信度                      |                 67 |                           36 |

**这直接反转了 E4-A 的拒绝归因**：原报告称"聚合/排序改善 −4、Schema 轻微恶化 +1"，修复后实为"聚合/排序恶化 +4、Schema 改善 −4"。拒绝结论不变（基于原始正确率），但"为什么拒绝"的解释此前是错的。

### 4.2 困难子集上 40% 的"失败"是数据集缺陷（两轮 F-Audit）

对 20 题样本逐题**实际执行 predicted 与 gold SQL 并比较结果集**（而非阅读 SQL 猜测）：

| 判定                                                      |        题数 |          占比 |
| --------------------------------------------------------- | ----------: | ------------: |
| 确认 gold 本身有缺陷                                      |           8 |           40% |
| 被误归类的输出契约问题（值 100% 正确，仅列选择/顺序不同） |           2 |           10% |
| evidence 与 gold 自相矛盾                                 |           1 |            5% |
| 执行验证后仍存在的真实歧义 / 倾向性判断                   |           3 |           15% |
| **确认为真实 Agent 错误**                           | **6** | **30%** |

其中"**缺 DISTINCT**"是跨 4 个数据库反复出现的系统性 gold 编写 bug（`bird_672`、`bird_963`、`bird_1252` 等）：题目问"多少个 X"，gold 却在一对多 JOIN 之后用不去重的 `COUNT(col)`，导致同一实体被重复计数。

**含义**：在 BIRD 的困难子集上，表面可见的改进空间远小于失败题数所暗示的。任何在此类子集上报告的机制收益，都应先扣除数据集缺陷部分。

### 4.3 可测得的"准确率提升空间"中，有一部分只是标注对齐

上述结论有一个可量化的直接证据。以 F-Audit 发现的"缺 DISTINCT"模式为例（`analysisDetail/annotation_convention_mining_2026-08-08.md`）：

- 该标注约定真实且稳定：train split 中 85.9% 的"计数+JOIN"gold 不使用 `COUNT(DISTINCT)`，eval core197 为 83.9%——两个 split 几乎相同。
- 模型系统性违反且方向完全一致：23 道可比题中 9 道不一致，**9/9 全部是"模型用了 DISTINCT、gold 没用"，反向 0 例**。模型写出的是语义上更正确的 SQL。
- 机械移除 DISTINCT 可使 **4 题转正 = +2.03 pp**，成本近乎为零——接近 E3-C 整个 Offline Schema 机制收益（+4.82 pp）的一半。
- **但转正题目中包含 F-Audit 经执行验证判定为 gold 缺陷的题目。** 该收益来自让模型复现标注缺陷，不是推理改善。

来源上完全合规（train-only 挖掘，不触碰 eval），但性质必须澄清：它提升的是**与该数据集标注习惯的一致性**，不是 Text-to-SQL 能力。这与 §4.2 的"40% 失败为 gold 缺陷"互相印证，共同说明：**该 benchmark 困难子集上的可测得 headroom 被显著高估，其中一部分只需对齐标注约定即可获得。**

#### 一个具体例子（`bird_1252`）

问题："在 Ig G 正常的患者里，**有多少人**有症状？"

|      | SQL                              | 结果        |
| ---- | -------------------------------- | ----------- |
| gold | `COUNT(T1.ID)`（不去重）       | **4** |
| 模型 | `COUNT(DISTINCT L.ID)`（去重） | **1** |

实际只有 **1 位**患者符合条件，但该患者在 Laboratory × Examination 的连接下产生 4 条行组合。问"多少人"，正确答案是 1。**模型答对了，被判错，因为标准答案错了。**

把模型的 `DISTINCT` 机械删除，使其复现 gold 的算法，该题即"正确"。这类题共 4 道，合计 +2.03 pp。

这个例子说明为什么"提分"与"能力提升"在此必须分开表述：该机制的作用机理是**让模型跟随标注者一起犯同一个错误**。

### 4.4 同配置重跑方差为 6 题（3 pp），此前被低估

`e3-c-conv` 与 `e3-c` run3 超参逐项对齐、只差后处理开关。利用逐题改写留痕还原出本次运行**后处理前**的成绩为 71/197，而 run3 为 77/197——**同配置两次运行相差 6 题**，模型侧逐题翻转为对→错 7 题、错→对 6 题，**SQL 逐字相同的仅 10.7%**。~~`temperature=0` 并不锁定输出，因为约 93% 的 completion token 是每次不同的隐藏推理~~ ——**该因果解释于 2026-08-11 被证否，真实原因是 `temperature=0` 从未被发送，见 §4.5**。

这是本项目首次直接测量重跑方差，此前只有从 Prompt 扰动实验估算的"±4 题"。两个直接后果：

1. **凡是基于单次运行、差异在 6 题以内的 profile 对比都不能作为结论。** 具体地，`e3-ac`（e3-c + 静态 patterns）得 70/197，比 e3-c 低 7 题，曾据此判断"静态 patterns 有害"——**该判断已收回**，−7 只比噪声大 1 题。
2. **不经过评分环节的测量不受此影响，应优先采用。** 同一对照中"模型违反标注约定的次数"为 24 vs 25，直接数 SQL 形态，据此得出的"把约定写进 Prompt 无效"依然成立。

详见 `rootcause/convention_postprocessing_2026-08-08.md` §四。

### 4.5 `temperature=0` 从未生效——所有运行都在采样

用一次实时探针核对 litellm 实际发送的参数：

```
传入 temperature=0  ->  实际发送 {'stream': False, 'reasoning_effort': 'high'}
传入 temperature=1  ->  实际发送 {'temperature': 1, 'stream': False, 'reasoning_effort': 'high'}
```

gpt-5 系模型**不接受 `temperature=0`**（调用会直接报 `UnsupportedParamsError`），而
`ours/recursive_db_rlm.py` 顶部设了 `litellm.drop_params = True`，于是该参数被静默丢弃、
以 API 默认值（gpt-5 为 1）运行。**本项目所有运行、所有 manifest、所有文档记载的
`temperature=0` 都不成立。**

三点后果：

1. **§4.4 的因果解释是错的。** 6 题重跑方差与 10.7% 的 SQL 逐字相同率，原本归因于
   「93% 的 completion token 是隐藏推理，每次不同」。真实原因简单得多：**采样从未被固定**。
   隐藏推理每次不同是这一点的结果，不是原因。
2. **方差无法通过配置消除。** 该模型只接受 `temperature=1`，因此 ±3 pp 的不确定度是这个
   模型上的固有属性，不是配置失误。要降低只能靠重复运行取均值。
3. **manifest 记录的是请求值而非发送值**，这个缺陷让上述问题隐藏了整个项目周期。已修：
   `shared/sampling_params.py` 向 litellm 查询实际发送参数，run manifest 新增
   `sampling_params_sent`（含 `temperature_sent`、`sampling_is_pinned`）。
   **旧运行的 manifest 无法追溯修正**，读取时须默认其 `temperature` 字段无效。

由此固化第五条实验纪律：**凡影响结果的参数，manifest 必须记录生效值而非请求值。**

### 4.6 两类未遂错误结论，及由此固化的实验要求

E6 实验（`rootcause/e6_recursion_2026-08-09.md`）先后产生过一个假阴性和一个假阳性，两者都几乎被写成定论：

- **假阴性**：两臂均得「0 转正」，看似干净否定递归。实为 10 题全部 `APIError`——脚本直接读环境变量取凭证，而本仓库 `.env` 使用 `api_key`/`azure_endpoint` 命名（正式 runner 经 `resolve_llm_config` 解析）；更糟的是异常被吞成 SQL 字符串，**基础设施故障被记录为实验结果**。同期另有一例：离线重评脚本自行推导数据库目录、路径不存在，使后处理看起来是 −3。
- **假阳性**：修复后首次运行 `bird_1175` 转正，看似支持"落地事实有效"。三次重复显示它只在 1/3 的运行中转正。

由此固化三条要求：

1. 实验脚本一律经 `resolve_llm_config` 取凭证、经 runner 常量取路径，不自行推导。
2. **异常一律不得吞为结果值**，失败即中止或单独记账；基础设施失败不进入转正率的分子分母。
3. **触发集实验必须重复至少 3 次。** 小样本单次观测在本项目中两个方向都能骗人（§4.4 的 6 题方差是其全集表现）。

### 4.7 方法论教训

`schema_join_diagnosis_2026-08-07.md` 曾仅凭阅读 SQL 文本判断 3 道题"predicted 与 gold 可能等价"，全部被随后的实际执行推翻。**任何"两条 SQL 是否等价"的判断必须实际执行比较结果集**——人工审查在这一步同样会出错，自动分类器靠正则更不可能做到。

## 5. 边界与限制

1. **数据集范围**：所有 E0 之后的实验使用 `bird_cleancore_ids.json` 的固定 197 题，其中 137 题（70%）是此前两次基线均失败的题目，60 题为对照。这是刻意构造的困难子集，**准确率数值不可与 BIRD Dev/mini-dev 全集直接比较**（本项目 legacy 全集数字为 69.2%，SQRL 为 70.6% BIRD Dev，同类量级；197 题子集的 39.09% 是另一个坐标系）。
2. **单次运行**：受预算限制，每个新配置通常只运行一次完整 197 题。**同配置重跑方差实测为 6 题（3 pp）**（§4.4），因此小于 3 pp 的变化不能作为结论，只能记为趋势；此前此处写"2 pp"，该阈值基于 Prompt 扰动的间接估算，偏低。确定性 系统侧干预（如约定后处理）不受此约束。
3. **隐藏推理不可见**：约 93% 的 completion token 是不返回内容的 reasoning token，句子级归因不可行。
4. **模型固定**：`azure/seminar-gpt-5.4-mini`，`reasoning_effort=high`，无 fine-tune 通道。**采样未固定**——请求中的 `temperature=0` 被静默丢弃，实际以 API 默认值运行（§4.7），该模型不接受 `temperature=0`，故方差不可通过配置消除。所有结论限定在"冻结商用模型"这一前提下。
5. **两个已知不稳定题**：`bird_1480` 在两个完全不同的机制改动下以相同症状回退，提示样本内存在对任意 Prompt 扰动敏感的题目，小样本 smoke 的 recovered/regressed 汇总应对此保持警惕。

## 6. 由本论点推出的行动约束

1. **不再设计强化 SC（自我检查/验证）的机制。** 四次失败已有统一解释（§2.2），第五次没有理由不同。
2. ~~**E6（受控递归）有原则地暂缓**~~ ——**已实测，见下**。原暂缓理由（分而治之要求模型可靠判断"哪个子计划需独立验证"，而模型连单步自检都不产生因果影响）本身站得住，但它只否定了**由模型决定分解**的形式。2026-08-09 改为 harness 确定性触发后实测了两个设计：

   - **粒度不变量触发**：定容即废弃。命中 4 题 / 误报 2 题，且其前提被证伪——BIRD 的 gold 自身在 47/114 的稳定失败中按扇出粒度聚合，"粒度正确"并非"答案正确"。
   - **空集触发 + E6-A/E6-B 等预算配对**（各 3 次重复）：两臂**统计上无法区分**（转正率 4.0% vs 4.3%，各自唯一一次转正都只出现在 1/3 的重复中且是不同的题），且都更容易毁掉本来对的题（33% / 67%，基线 10.4%）。**即使反馈内容是确定性机械测量、绝对可靠，相对纯重试仍无增益。** 这是本结论的第五次确认，也是最严格的一次。
   - 同一批题上，**确定性改写（空集时解除 `superlative_order_limit` 的守卫）是唯一可复现的正收益**：+1，零打坏，两次独立运行一致。

   **仍未被否定的是"强制结构约束"形式**（中间结果必须实际执行且不可绕过），它从未被测试，因为其触发条件在 197 题子集上没有靶子。要公平检验它，前置条件是构建能力失败密度更高的评测集。详见 `rootcause/e6_recursion_2026-08-09.md`。
3. ~~剩余方向集中在 PS/PG 阶段的信息供给，E5-A 是能力一的廉价验证入口~~ ——**E5-A 已完成并通过**（信息等价 197/197、可达性 11/11、无越权），但成本测量显示外部化是净负担（+109% token、+312% 延迟、准确率持平），根因是本任务上下文利用率仅约 4%，context store 针对的约束不存在。**E5-B 不建议作为准确率实验运行**：其两条接受轴（目标错误、token）先验都差——89–93% 的残留失败本已具备所需信息（查找不是瓶颈），而 E5-B 会进一步增加调用轮次。详见 `analysisDetail/e5_a_context_store_smoke1.md`。
4. ~~Query Mining（E3-D）可并行推进~~ ——**已诊断为不可行**：28 个 slot 全部未通过跨库门禁，最佳 slot 仅比模型自身判断强 1.5 pp，期望收益低于 Prompt 扰动噪声。门禁设计本身正确（它在拒绝交付不优于模型现有能力的建议）。E3-F 随之继续暂停。若重启，挖掘目标须从"问题→SQL 结构"（与模型能力重叠）改为"数据集书写约定"（如 F-Audit 发现的跨库 `COUNT(DISTINCT)` 缺失模式），并如实说明其性质是学习标注约定。详见 `analysisDetail/e3_d_query_mining_diagnosis_2026-08-08.md`。

   **该重定向已执行完毕**：三条约定（拼接 99.99%、最值写法 90.34%、计数去重 89.10%）从 train 挖出并通过跨库门禁，作为**确定性后处理**而非 Prompt 指令交付，两次独立测量均为 **+5 题**。同一批约定写进 Prompt 时效果为零（违反计数 24 vs 25）。详见 `rootcause/convention_postprocessing_2026-08-08.md`。
