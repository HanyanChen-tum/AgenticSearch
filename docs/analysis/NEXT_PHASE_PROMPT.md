## 这一阶段要做什么

按 `reasoning_trace_plan` 的 Phase 3–5，在**修正 gold** 上重做因果追踪。核心是找出
**模型从哪一句开始出错**，并验证干预能否提升准确率。

已有两个方法，都验证过、都有局限：

- **A `scripts/locate_first_wrong_sentence.py`** —— 定位「第一个错误承诺句」，要求给出可对数据库检验的断言。
  10 道一致性检验 **8/10 命中**；会偏早（`bird_93` 抓到「我应该核实拼写」这种反向句），短推理时不可靠。
- **B 前缀续写重采样** —— 把前 k 句摘要当上下文让模型续写，测 k 变化时答案分布移动。
  在 `bird_48` 上精确定位到第 3 句（与 A 和人工判读三方一致），还多找出「即使保留条件也不知道正确列名」这一层。
  局限：前缀是**摘要**不是原始 CoT，模型是被「告知」它想过什么。

建议流程：**A 扫全量 → B 验证关键的十几道 → 人工抽 20~30 道做基准校准**。

## 六个必须避开的坑（都是这一轮踩过的）

1. **推理必须内联捕获，不能事后回放。** `capture_reasoning.py` 回放的推理**可能对不上原始运行**——
   它自己的 docstring 点名 `bird_93`：回放时模型查了数据库，原始运行没查。
   要真实推理：用带 `reasoning_capture` 的 profile 跑，数据在 `attempts[].reasoning_capture`（**不在顶层**）。
   已有语料：`docs/analysis/analysisDetail/reasoning_inline_{ctl,trt}_turn1.json`（原始数据集，各约 460 题）。
   ⚠️ `reasoning_sentence_labels_163.json` **是回放数据，已作废，勿用**。
2. **关键词启发式在这份语料上不可信。** 它产出过两个自洽但错误的结论：
   「模型因认定工具不可用而放弃核实」（四组工具调用率都是 94~100%，机制不成立）、
   「想核实是最强失败信号 −17.3pp」（反向因果，它是难度代理）。用 LLM 标注 + 执行验证。
3. **LLM 标注器和被研究模型是同一个**（`azure/seminar-gpt-5.4-mini`），有自评偏差。
   findings.md 记着本项目的 LLM judge 只有 2/15 正确。**出结论前先做人工一致率检验。**
4. **比较前先查 `agent_config_sha256`。** 有三组运行是同配置不同名字，直接排名会把噪声当效应。
5. **`reasoning_capture` 走 Responses API，准确率与 Chat Completions 基线不可比**，只能同类互比。
6. **9 个老运行不可用**（`bird_nofs_rhigh` 等）：无 cfg_sha、无 trace、走出过泄漏事故的 in-domain 检索、
   违反导师指令「eval set 一律不碰」。B1/B2 例外，它们不检索，可用。

## 关于递归（论文主题）

**递归极少被真正调用**：`e3-c-recursive` dev500 只有 19/500（3.8%）；
`e3-c-recursive-db` dev200 四次分别 4.0% / 15.1% / 15.6% / 14.6%——**温度为 0 却波动近 4 倍**。

所以任何**关于递归的**结论都必须**同时报两个数**：全集效应（会被稀释）和仅在调用过递归的
题上的效应（单独报是选择性报告）。有效样本只有 8~31 题。

**这条只适用于递归，不要外推成"任何 RLM 结论"。** RLM 是三个机制
（见 [`README.md` §2.3](README.md)），另外两个——可执行环境、程序化探索——**每题都在生效**，
不存在"调用率"，直接看全集即可。把这条规则套到整个 RLM 上，会把一个只在 13% 题上触发的
机制的统计口径，错误地施加到两个 100% 触发的机制上。
