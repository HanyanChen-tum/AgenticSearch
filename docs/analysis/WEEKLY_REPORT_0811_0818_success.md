## 一、准确率改进

| 改动 | 效果 |
|---|---|
| 修复控制台编码崩溃 | 两个推理臂各 **+2.2pp**；`arcwise_full` 84.5% → **86.7%** |
| 关闭两条改语义的 convention 规则 | 修正 gold 上正向 |

### 1.1 编码崩溃修复

本机控制台是 cp936，数据库行含编不出的字符即抛 `UnicodeEncodeError`，
异常被当作模型的真实失败、`correct=False` 落盘。

**`bird_847`：模型查对了 `Räikkönen`，`ä` 编不进 cp936，于是记为答错。**

它有选择性、不是随机噪声——被杀的是答案含非拉丁字符的题，
按库高度集中（`card_games` 12%、`formula_1` 8%），同时扭曲总分和分层分析。

新增 `shared/console.py` 的 `force_utf8_console()`，在流层面重配 stdout/stderr，
已接入全部 5 个 agent 入口。

### 1.2 convention 规则的判据

`count_no_distinct` 在 JOIN 查询里删掉 `COUNT` 的 `DISTINCT`，
依据是 train gold 上 2377 样本、**0.891 支持度**。

但修正版 gold 把 DISTINCT 用量从 83 题提到 130 题（**+57%**）——
**那 0.891 度量的不是 SQL 语义，是标注者漏写 DISTINCT 的习惯。**

`bird_1505`（题面 "how many **customers**"）：

```
模型写的（对）     COUNT(DISTINCT T1.CustomerID)
harness 改成（错） COUNT(T1.CustomerID)
原始 gold（也错）  COUNT(*)
```

**建立的判据（可预判，不需实验）：**

| 规则 | 改的是什么 | 判决 |
|---|---|---|
| `no_select_concat` | **输出形状**——拆成两列，数据一字节没变 | 保留 |
| `count_no_distinct` | **计算语义**——COUNT 的对象从实体变成行 | 关闭 |
| `superlative_order_limit` | 计算语义，且会丢掉 WHERE 条件 | 关闭 |

> harness 后处理可以规整输出格式，不可以改变查询算的是什么。

判据写进 `build_sql_conventions.py` 的 `SEMANTICS_CHANGING`——
该脚本按支持度重算 `enabled`，只改产物会被下次重跑复活。

## 二、发现：163 道失败的责任归属

逐题读【题面】【hint】【双方 SQL】【双方执行结果】，必要时下探数据库跑反证查询。
163 道全部定责，其中 **150 道人工判读**。

**结果：gold : 模型 = 61 : 30。**

其中约 27 道是执行即可证伪、与读题无关的 SQL bug：

| 机制 | 实例 |
|---|---|
| AND/OR 缺括号导致条件退化 | `bird_1265` gold 算出 47，正解 35 |
| 文本列当数值排序 | `bird_879` 取到 `'91.610'`，真实最大 257.32 |
| NULL 在 ASC 排最前被取到 | `bird_847` 取到无成绩的车手 |
| join 扇出放大聚合 | `bird_198` 得 732.1，正解 20.25 |

已发布为独立台账页面 `fault_ledger_163.html`。

## 三、外部数据独立验证

用 VLDB 2026（arXiv:2601.08778）另一团队重标的修正版 gold 交叉验证。
关键设计是把两个混在一起的变量拆开：

| 列 | 模型答案 | 判分标准 |
|---|---|---|
| A | 原答案 | 原 gold |
| B | **同一份原答案** | 修正 gold |
| C | 新运行答案 | 修正 gold |

| | 干净子集 277 | **纯 gold 修正 74** |
|---|---:|---:|
| A 原答案 × 原 gold | 81.9% | **50.0%** |
| B 原答案 × 修正 gold | 87.7% | **71.6%** |
| C 新运行 × 修正 gold | 86.3% | 70.3% |
| **换参考答案的贡献** | **+16** | **+16** |
| 重新采样的贡献 | −4 | −1 |

**74 道纯 gold 题（题面与 hint 一字未改）上，模型答案一个字节没变，判分从 50.0% 升到 71.6%。**

由错变对的 26 道中，**19 道正是第二节独立判为 `gold` 的题**——
读题面+执行反证、另一团队独立重标、模型答案不变而判分翻正，**三条证据线汇合**。

## 四、错误源头逐层定位（163 道）

按 SQL 构造流水线机械判定**最先**在哪一层与 gold 分歧（sqlglot 解析，不用 LLM）。

| 最先出错的层 | 题数 | 占比 |
|---|---:|---:|
| 过滤列 | 35 | 21.5% |
| **表选择** | **33** | **20.2%** |
| JOIN 键 | 24 | 14.7% |
| 聚合函数 | 22 | 13.5% |
| 纯格式/列序 | 11 | 6.7% |
| 多用了表 | 10 | 6.1% |
| 投影列数 / 过滤字面量 / 分组 / 排序 LIMIT | 27 | 16.5% |

对表选择类的 33 题，逐一核对 gold 需要、而预测漏掉的那张表当时有没有被检索给模型：

| 情况 | (题,表) 对数 |
|---|---:|
| 未检索到（漏检） | **0** |
| 检索到但未选中 | **0** |
| **检索到、已选中、模型却没用** | **37** |

**可以改进模型什么：**

1. **"改进 schema 检索"这条路对本类错误已被排除**——37/37 不存在检索缺口，
   表召回率 98.4% 印证。再往检索上投入是浪费。
2. **占比最大的"过滤列"（21.5%）才是真正的模型错误集中区**，
   而不是看起来最像方法问题的表选择。
3. 表选择层 33 题里 **23 题是"gold 比模型多连了一张表"**，模型写的是更简洁的查询；
   交叉核对后 gold 缺陷 20 题、模型真实错误仅 2 题。
   **这类分层统计必须先剔除 gold 缺陷再读。**

## 五、「结果形状」决策点的完整分解（20 个案例，全部因果验证）

信息增益排名第二的信号（答对率极差 55.3%）：

| 子类型 | 题数 | 代表题 |
|---|---:|---|
| **最值题不查并列（该查没查）** | **3–4** | `bird_1092`（8/8 确定性复现）、`bird_930`（10/10） |
| 原失败纯属偶然，重采样即自愈 | 4 | `bird_798`、`bird_483`、`bird_213`、`bird_149` |
| gold 本身有逻辑 bug | 3 | `bird_1322`、`bird_529`、`bird_1399` |
| 并列方向反了 | 2 | `bird_1135`、`bird_41`（`ROW_NUMBER` vs gold 要的 `RANK`） |
| 是非题该给 YES/NO 字面量 | 2 | `bird_473`、`bird_1399` |
| 输出契约/多问句遗漏 | 1 | `bird_530` |
| 模型把简单题复杂化 | 1 | `bird_637` |
| 输出列拼接/格式约定 | 1 | `bird_1011` |
| **定冠词单数措辞触发 `LIMIT 1`** | 1 | `bird_412`（"the card by artist X" 实际匹配 50 张） |

**可以改进模型什么：** 唯一可推广的机制是「**未经验证就假定唯一**」——
`bird_412` 把它从"最值题"扩展到**任何定冠词单数措辞**，覆盖面比最初以为的大。
改进要发生在**模型自己下笔前的推理里**（先确认"是不是真的只有一条"）。
