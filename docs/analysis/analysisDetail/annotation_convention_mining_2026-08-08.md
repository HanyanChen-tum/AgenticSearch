# 标注约定挖掘可行性：DISTINCT 案例（2026-08-08）

## 动机

E3-D 诊断（`e3_d_query_mining_diagnosis_2026-08-08.md`）判定"问题表述 → SQL 结构"的挖掘不可行，因为它与模型已有能力重叠（最佳 slot 仅强 1.5 pp）。该诊断同时提出一个可能有价值的替代方向：挖掘**数据集标注约定**——模型不可能自行推断、但可从 train split 合规获得的信息。

F-Audit 已识别出一个候选：**"缺 DISTINCT"** 跨 4 个数据库反复出现——题目问"多少个 X"，gold 在一对多 JOIN 之后使用不去重的 `COUNT(col)`，导致同一实体被重复计数。本文档量化该约定是否真实、可迁移、且值得挖掘。纯离线分析（sqlglot AST + SQLite 执行），无 LLM 调用。

## 结果一：约定真实存在且稳定可迁移

限定于"计数类问题（how many / number of / count of）+ gold SQL 含 COUNT + 含 JOIN"这一可判定子集：

| | train split | eval core197 |
|---|---:|---:|
| 可比较题数 | 1,598 | 31 |
| **不使用** `COUNT(DISTINCT)` | **85.9%**（1,372） | **83.9%**（26） |
| 使用 `COUNT(DISTINCT)` | 14.1%（226） | 16.1%（5） |

**一致性约 85%，且 train 与 eval 几乎完全相同（85.9% vs 83.9%）。** 这不是噪声，是稳定的标注约定，且可跨 split 迁移。

## 结果二：模型系统性违反该约定，方向完全一致

对 E3-C run3 的 197 题，比较模型预测 SQL 与 gold 在该维度上的一致性：

| | 数量 | 占比 |
|---|---:|---:|
| 可比较题数 | 23 | — |
| 与 gold 约定一致 | 14 | 60.9% |
| **不一致** | **9** | **39.1%** |
| 　模型用了 DISTINCT、gold 没用 | **9** | **100%** |
| 　gold 用了、模型没用 | **0** | 0% |

**9/9 单向**——模型比 gold 更严格地去重。这是系统性偏差，不是随机差异。9 题中 7 题被判为错误。

## 结果三：机械照做可换取 +2.03 pp

对 7 道判错题机械移除 `COUNT(DISTINCT` → `COUNT(`，重新执行并与 gold 比对：

| 题目 | 结果 |
|---|---|
| `bird_1505` | 转为正确 |
| `bird_1252` | 转为正确 |
| `bird_1267` | 转为正确 |
| `bird_672` | 转为正确 |
| `bird_1254`、`bird_963`、`bird_474` | 仍错（另有其他原因） |

**4 题转正 = +2.03 pp**，在 197 题上，成本几乎为零（一条约定注入，无额外调用轮次）。

作为对照：这个幅度接近 E3-C 整个 Offline Schema 机制的一半收益（+4.82 pp），而实现复杂度低一个数量级。

## 但这里有一个必须正面说明的问题

**转正的 4 题里，`bird_672`、`bird_1252`、`bird_1267` 中的前两道，正是 F-Audit 中经逐题执行验证后被判定为 `DATASET_OR_GOLD_CONFLICT`（gold 本身有缺陷）的题目**（见 `filter_audit.md`）。当时的判定依据是：题目问"多少个患者/多少个用户"，gold 未去重导致同一实体被其多条子表记录重复计数，**模型的 `COUNT(DISTINCT ...)` 在语义上更正确**。

也就是说：

> **这个机制之所以能提分，是因为它让模型复现数据集的标注缺陷，而不是因为它让模型推理得更好。**

而 F-Audit 的结论文件里明确写着这些题"不应计入任何后续机制的'待恢复错误'分母"。若现在用一个机制去"修复"它们，等于自相矛盾。

### 合规性与科学性是两个不同的问题

| 维度 | 判断 |
|---|---|
| **来源合规性** | **通过**。约定完全从 train split 挖掘，不使用任何 eval gold、eval 错误或评分反馈。符合项目全部 provenance 规则。 |
| **是否提升 benchmark 分数** | **是**，+2.03 pp，且成本极低。 |
| **是否提升 Text-to-SQL 能力** | **否**。模型原本写出的是语义更正确的 SQL；该机制教它写得不那么正确，以匹配标注习惯。 |

监督学习里"学习标注约定"是标准做法，train split 内的约定本来就是可用信号。所以这不是作弊。但把它报告为"提升了 Text-to-SQL 准确率"是误导——它提升的是**与该数据集标注习惯的一致性**。

## 建议

若要实现，**必须满足两个条件**：

1. **作为独立、可关闭的机制单独报告**，不与语义机制混在同一个准确率数字里。报告时同时给出"开启/关闭"两组数字。
2. **在结论中明确标注其性质**：这部分收益来自对齐数据集标注约定，不代表查询语义能力提升。相应地，F-Audit 认定的 gold 缺陷题目应在"语义能力"口径下继续排除，只在"benchmark 对齐"口径下计入。

**这条发现本身的价值可能高于那 +2 pp。** 它给出了一个可量化的证据：**BIRD 困难子集上，一部分可测得的"准确率提升空间"实际来自标注约定而非查询能力**——这与 F-Audit 测得的"40% 的失败是 gold 缺陷"相互印证，共同支撑 `../SYNTHESIS.md` 的第二条独立结论（该 benchmark 表面可见的 headroom 被显著高估）。

对论文而言，"我们量化了 benchmark 分数中有多少来自标注对齐"比"我们又提了 2 个点"是更有意思的结论。
