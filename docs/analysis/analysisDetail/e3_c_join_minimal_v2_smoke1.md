## 新增回退细节：都跟 JOIN 逻辑无关

- **`bird_1480`**：v1正确输出`substr(Date,5,2) AS Month`（月份），v2输出了完整的`y.Date`——纯输出契约回退，跟JOIN类型/数量无关。**这题在机制二（已拒绝的字面量核实提醒）的N=44测试里也回退过，且是同一个症状**（月份输出被换成完整日期）。两次完全不同的机制改动都让这同一道题在同一个方向上出错，说明这道题本身可能对任何 Prompt 扰动都敏感，不是v2措辞的特定问题。
- **`bird_877`**：v1正确输出两个独立列`forename, surname`，v2把它们拼接成了一列`forename || ' ' || surname`并加了不必要的DISTINCT——这违反的是"不要拼接列"的一般输出规则，同样跟JOIN逻辑无关。

## 判断

**v2 的目标修复本身是成功的**（`bird_27`确认修好，验证了"精确措辞可以定点修复特定失败模式"这个方法论本身有效），但两次独立的小样本测试（v1、v2）都在同一道无关问题（`bird_1480`）上出现回退，且回退症状与机制二在完全不同机制下产生的回退高度相似（同一题、同一种"月份变日期"的输出契约错误）。这指向一个比"这条提示该怎么写"更基础的问题：**这批小样本里存在对任何 Prompt 扰动都不稳定的"脆弱题"，N=26 这个规模不足以把这种题级噪声和机制的真实净效应分开**。继续在同一小样本上迭代措辞，有陷入方法论红线（用固定小样本的具体失败反复调 Prompt）的风险。

## 结论与建议

不建议继续在 N=26 上迭代第三版措辞。当前证据状态：

- 机制"精简 JOIN 数量"本身在 v1/v2 两轮里稳定恢复了 `bird_1175`、`bird_24` 这两道结构清楚的过度连接题，这个子效果目前看比较可信。
- "分开表数量和JOIN类型"这条 v2 追加规则，定点修复了它针对的问题，但样本太小，无法判断是否会稳定引入新的无关副作用，还是这次恰好撞上了本身就不稳定的题目。
- `bird_1480` 连续两次在不同机制下用相同方式回退，值得单独标记为"不稳定题"，后续任何机制评估都应该把它单独看待，不能简单计入 recovered/regressed 汇总。

**下一步两个选项**：(a) 停止在这个方向上继续手调措辞，把 v1（不含v2追加规则）作为候选，一次性扩大到类似机制二 N=44 的分层样本做正式判定，不再迭代文字；(b) 搁置该机制族，回到 Schema/Join 诊断或 F-Audit 里其他尚未验证的方向。两者都不应该再基于 N=26 的具体题目继续手动调整提示文字。
