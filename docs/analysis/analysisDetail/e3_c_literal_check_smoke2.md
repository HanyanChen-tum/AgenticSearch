# FINAL 前未核实字面量警告：N=44 扩大 Smoke 结果与决策（2026-08-07）

## 范围

对第一轮 N=8（见 `e3_c_literal_check_smoke1.md`）的"样本太小、无法判断"结论做扩大验证。按数据库分层抽样，覆盖全部 11 个数据库：每个数据库取 e3-c 基线下**当前失败**的前 2 题（22 题，`targets_currently_failing`）+ **当前正确**的前 2 题（22 题，`regression_controls_currently_correct`），共 44 题，ID 见 `data/processed/e3_c_literal_check_smoke2_ids.json`。运行结果：`results/e3_c_literal_check_smoke2.json`，trace：`trace/e3_c_literal_check_smoke2/`。

## 结果：净回退，且回退与机制目标无关

| 指标 | 数值 |
|---|---:|
| e3-c 基线（同 44 题） | 22/44 = 50.0% |
| + literal-check | 18/44 = 40.9% |
| 恢复（原失败→现正确） | **0** |
| 回退（原正确→现失败） | **4** |
| 双方都对 | 18 |
| 双方都错 | 22 |

22 道目标题（e3-c 下原本就失败）里，有 11 道题的新预测 SQL 里仍然存在"字面量比较、未经 sample_values 核实"的模式——**这 11 道里 0 道被机制修正**。也就是说，即便限定在机制最应该起作用的场景里，恢复数依然是 0。

## 4 道回退题：全部与字面量无关

| ID | 数据库 | 回退原因 |
|---|---|---|
| `bird_1480` | debit_card_specializing | 输出列从"月份"变成了整个"日期"字段，且改用完整日期分组，纯输出契约/聚合粒度回退 |
| `bird_1039` | european_football_2 | 多输出了一个 `player_name` 列并加了不必要的 `GROUP BY`，纯输出契约回退 |
| `bird_877` | formula_1 | 新版本 `predicted_sql` 为空字符串——模型这次没能在预算内产出合法 FINAL SQL |
| `bird_27` | california_schools | JOIN 类型从 `LEFT JOIN`（正确，保留无 satscores 记录的学校）退化成 `INNER JOIN`（丢行） |

四道回退分别是输出契约×2、运行失败×1、Join类型×1——**没有一道跟字符串字面量核实有任何关系**。这与第一轮 smoke1 里 `bird_1171` 的回退模式一致（那道题也完全不涉及字面量，却在加了警告后从"正确的减法年龄计算"退化成"直接比较年份"）。两轮加起来看，回退集中出现在跟机制设计意图无关的地方，指向同一个解释：**往上下文里追加额外文本（即使内容本身是有道理的软提示），会对模型在同一条 trace 里其它无关判断产生可观测的负面扰动**，这个副作用目前观察到的量级超过了机制本身在目标场景上的收益（收益目前观测为 0）。

## 决策

**拒绝当前实现的"FINAL 前未核实字面量警告"机制。** 判定依据：

1. 目标场景 0 恢复（22 道当前失败题，11 道明确命中机制设计场景，无一修正）。
2. 4 道回退，且回退原因与机制设计意图无关，指向"扩展上下文本身有副作用"这个比机制内容更基础的问题。
3. 净变化 -4/44（-9.1pp），远超"约 2pp 内只算趋势"的判定线，且方向明确为负。
4. 44 题分层覆盖全部 11 个数据库，不是单一数据库的偶然波动。

第一轮 smoke1 里 `bird_1267` 展示过机制"精确按设计工作"的证据（模型确实去查了 `sample_values` 并把字面量改到跟 gold 完全一致），这个观察本身没有错——但本轮结果说明，即使机制局部生效，也不足以把题目最终改对（往往还有其它独立 bug），而扩展上下文带来的整体副作用是净负的。

## 与项目已有结论的关系

这与 E1（strict verified-final）被拒绝的证据结构相似：一个从直觉上合理的"让模型多验证一步"的机制，实际测量下来是净成本、无净收益。但机制本身和 E1 不同——E1 是无差别硬阻断所有 FINAL、代价是调用数和 token 翻倍；这次是从不阻断的软提示、代价是额外的上下文长度和可能的注意力扰动。两次独立测试都指向同一个更一般的教训：**在这个 harness 里，任何形式的"额外提醒/额外验证步骤"，即使设计得再有针对性，都需要先证明净收益为正，不能假设"多一层检查总是更安全"**。

## 代码去留

`ours/agent/state.py` 的 `find_unverified_literal_columns`/`AgentExecutionState.record_sample_values`/`unverified_literal_warning`，`ours/recursive_db_rlm.py` 的 warning 注入，以及 `e3-c-literal-check` profile 予以保留在代码库中（默认关闭，`literal_verification_nudge=False`），不删除、不在任何默认 profile 上启用。保留原因：便于未来如果有新证据支持"选择性触发"（比如只在特定高风险列类型上触发，或降低触发频率避免上下文膨胀）时复用现有代码骨架，而不必重新实现追踪逻辑。当前实验记录明确标注为已拒绝，不作为下一步机制候选。
