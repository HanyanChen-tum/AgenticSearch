# 防御性过度 JOIN 提醒：机制实现与 N=26 Smoke 结果（2026-08-07）

## 机制实现

源自 Schema/Join 深度诊断（`schema_join_diagnosis_2026-08-07.md` §3.3）的"防御性过 Join"模式——模型不确定时倾向于多连一张表兜底。与已拒绝的机制二（FINAL 前未核实字面量警告）在架构上刻意不同：这是**固定长度的静态协议文字**，从对话第一轮起就存在于 system prompt 里，不随 trace 逐轮累积新文本。

- **实现位置**：`ours/agent/prompts.py` 新增 `basic-join-minimal` = `basic` + 一条协议规则："只连接回答问题真正需要的最小表集合，只有当某个输出列/过滤条件/明确要求的关系确实依赖某张表时才连接它；两种写法同样能回答问题时优先选 JOIN 更少的那个。"不含任何数据库/题目特定内容，`contains_task_specific_sql_rules=False`、`contains_examples=False`，保持"protocol-only"来源，不违反 eval 调参红线。
- **新 profile**：`e3-c-join-minimal`，与 `e3-c` 唯一差异是 `prompt_profile`。
- **测试**：新增 prompt 内容测试（协议-only、包含目标语句、哈希与 basic 不同）+ profile 边界测试（除 prompt_profile 外与 e3-c 完全一致）。全部 93 个仓库测试通过。

## Smoke 范围与结果

**目标题的筛选是客观、可计算的**（不依赖读 eval gold 语义，只是结构比较）：扫描 e3-c 全部 120 条失败，取 predicted SQL 的表集合是 gold 表集合真超集的题目（模型比 gold 多连了至少一张表，且连的表包含了 gold 需要的全部表）——120 条里恰好 12 条满足，全部纳入目标集；另按数据库分布配 14 道当前正确题作防回归对照，共 26 题，覆盖 7 个数据库。

| 指标 | 数值 |
|---|---:|
| e3-c 基线（同26题） | 14/26 = 53.8% |
| + join-minimal 提示 | 15/26 = 57.7% |
| 恢复 | **2**（`bird_1175`、`bird_24`） |
| 回退 | **1**（`bird_27`） |
| 净变化 | **+1** |

## 逐题细看：恢复的原因和机制设计意图直接吻合

- **`bird_1175`**（thrombosis_prediction，目标题之一）：基线用 `INNER JOIN Examination`，新版本改成 `LEFT JOIN Examination` 并配 `COALESCE` 兜底——模型意识到 `Examination` 不是每一行都必然存在匹配，从"强制内连接可能丢行"转向"外连接+容错"，直接命中机制想解决的问题。
- **`bird_24`**（california_schools，目标题之一）：基线连了 `schools`+`frpm`+`satscores` 三张表，`schools` 其实是多余的（gold 只用 `frpm`+`satscores`），而且从多余的 `schools` 表里错误取用了输出列。新版本去掉了 `schools`，只连必要的两张表，同时输出列来源也随之选对了。这是"少连一张表"直接带来"选对输出列"的连带修正，超出了机制字面设计的预期收益。
- **`bird_27`**（california_schools，回退）：基线原本正确地用 `LEFT JOIN satscores`（保留没有 SAT 成绩的学校，匹配 gold 语义），新版本却改成了 `INNER JOIN`——这是提示语被**误泛化**的一个具体案例：Prompt 说的是"少连不必要的表"，但模型可能把"精简 JOIN"的整体倾向也套用到了"JOIN 类型选择"上（LEFT→INNER 被当成"更简单"），而这两者是不同的维度。这是当前提示文字的一个可辨认、可修的具体缺口，不是无法解释的旁支扰动。

## 与机制二的对比：回退的性质不同

机制二（已拒绝）的 4+1 次回退全部发生在**跟机制目标完全无关的地方**（输出列、聚合粒度、运行失败），只能归因于"扩展上下文本身有副作用"，没有可操作的改进方向。这次唯一的回退（`bird_27`）**直接命中同一个语义维度**（JOIN 相关决策），且原因可以清楚指认（"精简"被泛化到了"JOIN类型"而不只是"JOIN数量"）——这是一个可以通过修改提示措辞收窄范围来解决的具体问题，例如把提示改成明确区分"只精简表的数量，不改变必要的 JOIN 类型（LEFT/INNER）选择"。

## 结论

**N=26 显示净正向信号（+1，53.8%→57.7%），且恢复和回退都能对应到机制的具体作用机制，不是无法解释的噪声。** 这与机制二"净负、且回退原因跟机制无关"的证据结构明显不同，值得继续验证，但样本量仍然太小（按项目标准，个位数题目的净变化只能算趋势），且已经发现了一个具体、可能通过收紧提示措辞规避的回退模式。

## 下一步建议

1. 不直接接受或拒绝，先按发现的问题微调提示措辞（明确"精简表数量"和"不要因此弱化 JOIN 类型选择"是两件事），产出 v2 提示。
2. 用同一批 26 题（外加 `bird_27` 这类"依赖 LEFT JOIN 保完整性"的题目单独再抽几道做针对性回归检查）重跑 v2，确认回退是否消失。
3. 如果 v2 稳定，再扩大到更大样本（类似机制二 N=44 的分层设计，覆盖全部 11 个数据库）做正式判定；样本扩大前不应该把 26 题的 +1 写成正式结论。
