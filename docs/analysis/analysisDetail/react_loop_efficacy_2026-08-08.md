# ReAct 循环有效性测量：自我纠正到底起不起作用（2026-08-08）

## 为什么做这个测量

此前所有轨迹审计（`e3_c_schema_v4_trajectory_audit.md`、`e4_a_core197_run1_trajectory_audit.md`）都只统计**失败题**，因此"失败集里 0 次 wrong→correct 恢复"这个结论带有循环论证性质——真正被循环救回来的题，最终是正确的，根本不会进入失败集。

本次把同样的执行状态转移分析跑在**全部 197 题**上，让正确题和错误题可以直接对比。纯离线分析，不消耗任何 LLM 调用。脚本：`react_loop_efficacy.py`、`final_sql_verified.py`（scratchpad，未入库）。

## 结果一：循环有效，但呈极端二值

| 运行 | 正确题恢复率（wrong→correct） | 错误题恢复率 |
|---|---:|---:|
| E3-C run3 | 4/77 = 5.2% | **0/120 = 0.0%** |
| E0 run1 | 3/69 = 4.3% | **0/128 = 0.0%** |
| E0 run2 | 9/66 = 13.6% | **0/131 = 0.0%** |

循环**不是装饰性的**——三次运行里分别有 4、3、9 题是先执行出错误结果、再靠 observation 反馈改对的。这否定了"多轮 ReAct 完全不起作用"这个可能的假设。

但错误题的恢复率是**精确的 0，三次运行无一例外**。更关键的是"是否曾执行出匹配 gold 的结果"：

| 运行 | 正确题曾执行出正确结果 | 错误题曾执行出正确结果 |
|---|---:|---:|
| E3-C run3 | 34/77 = 44.2% | **1/120 = 0.8%** |
| E0 run1 | 38/69 = 55.1% | **1/128 = 0.8%** |
| E0 run2 | 39/66 = 59.1% | **2/131 = 1.5%** |

**失败题不是"差一点对、循环没抓住"，而是从头到尾就没接近过正确答案。** 99% 以上的失败题在整条轨迹里从未执行出过匹配 gold 的结果。循环没有可救的东西。

## 结果二：模型不会因为"要出错"而多探索

| 运行 | 正确题执行次数/题 | 错误题执行次数/题 | 正确题多次执行占比 | 错误题多次执行占比 |
|---|---:|---:|---:|---:|
| E3-C run3 | 1.22 | 1.38 | 27.3% | 30.0% |
| E0 run1 | 1.46 | 1.52 | 37.7% | 36.7% |
| E0 run2 | 1.64 | 1.51 | 36.4% | 36.6% |

两组的探索量几乎相同（错误题甚至略多）。模型**没有表现出任何"察觉到不确定就多查一下"的自适应行为**——它在即将答错时的探索强度，和答对时没有区别。8 轮迭代预算实际平均只用了 1.2-1.6 次执行。

这正是 SQRL 论证的那个 gap：inspection 决策是训练出来的能力，不是给了工具就会用。

## 结果三：多数正确答案根本没被执行验证过

问一个更严格的问题——**最终提交的那条 SQL 本身，有没有在轨迹里被执行过？**

| 运行 | 分组 | FINAL 被执行过 | FINAL 从未执行 | 完全没调用过 db.execute |
|---|---|---:|---:|---:|
| E3-C run3 | 正确 | 27/77 = 35.1% | **50/77 = 64.9%** | 15 = 19.5% |
| E3-C run3 | 错误 | 22/120 = 18.3% | 98/120 = 81.7% | 17 = 14.2% |
| E0 run1 | 正确 | 22/69 = 31.9% | **47/69 = 68.1%** | 6 = 8.7% |
| E0 run1 | 错误 | 17/128 = 13.3% | 111/128 = 86.7% | 13 = 10.2% |
| E0 run2 | 正确 | 24/66 = 36.4% | **42/66 = 63.6%** | 8 = 12.1% |
| E0 run2 | 错误 | 22/131 = 16.8% | 109/131 = 83.2% | 17 = 13.0% |

**约 2/3 的正确答案，其提交的 SQL 从未被执行验证过**；其中 9-20% 的正确答案甚至全程没调用过一次 `db.execute`——纯靠 schema 和 Hint 一次写对。

顶层 README 对 harness 的核心描述是："it can run exploratory SQL, inspect stored values, **test its query, see real results, and only then submit**"。数据显示这个描述**只覆盖了约三分之一的正确答案**。剩下三分之二是模型直接写出来的，执行环境没有参与验证。

需要说明的边界：`FINAL 被执行过` 用的是规范化后的 SQL 文本精确匹配。模型执行 SQL_A、提交语义等价但写法不同的 SQL_B，会被计为"未执行"。所以真实的"验证过"比例应略高于 31-36%，但这个偏差同时作用于正确和错误两组，不影响组间对比，也不影响"多数正确答案未经 FINAL 级验证"这个方向性结论。

## 综合解读

三条结果拼起来是一致的图景：

1. **失败在第一次执行之前就已经决定了。** 失败题 99% 从未接近正确答案，循环恢复率精确为 0。这与轨迹审计早先的发现（81-106/126 的失败在首次 `db.execute` 就已偏离）、以及 E4-A 的发现（82/126 是"计划被忠实执行但计划本身错了"）完全吻合。
2. **循环的真实贡献很小但非零**：每次运行 3-9 题（占正确题的 4-14%）。它值得保留，但它不是准确率的主要来源。
3. **执行环境作为"验证器"的实际使用率远低于设计意图**：约 2/3 的正确答案未经 FINAL 级执行验证。

这解释了本项目此前**四个失败机制的共同命运**（E1 强制验证、E4-A QueryPlan、字面量核实提醒、JOIN 精简提示）：它们全都在试图强化"自我检查/验证"这一环，而数据显示这一环对失败题的边际价值接近零——**失败题没有可供检查的正确候选，再强的检查机制也检查不出正确答案**。这不是四次独立的设计失误，是同一个结构性原因。

对照 Thought Anchors 的框架：决定性的 anchor 在 PS（问题设置）/PG（计划生成）阶段，而 SC（自我检查）阶段的因果影响接近零——本项目在动作层独立复现了这一结论。对照 SQRL：同样的推理架构下，他们通过 execution-based RL 让模型学会"何时该探查、探查什么"，而本项目在冻结的闭源模型上无法训练，只能用指令，指令被证明无效。

## 对后续计划的影响

1. **不应再设计任何强化 SC（自我检查/验证）的机制。** 四次失败已有共同解释，第五次没有理由会不同。
2. **E6（受控递归）应当有原则地暂缓，而不只是"排在后面"。** 分而治之的前提是模型能可靠判断"哪个子计划需要单独验证"——而数据显示模型连单步的自我检查都基本不产生因果影响，且不会自适应地增加探索。在这个前提未改变之前，Leaf 机制缺少可信的触发依据。这个理由本身应写入实验计划作为 E6 的暂缓依据，比"E4-A 未通过所以暂停"更根本。
3. **剩余可做的方向集中在 PS/PG 阶段的信息供给**，也就是本项目唯一成功的 E3-C 所属的类别（改变模型看到什么，而不是告诉模型怎么做）。E5-A（同信息外部化 smoke）属于这一类且成本低，是能力一仅存的廉价验证入口。
4. **本结果本身是可发表的负面结论**：在冻结商用模型上，harness 层的验证类干预存在结构性天花板，因为失败在验证环节介入之前就已确定。SQRL 提供了对照（同架构 + 训练 = 突破），Thought Anchors 提供了方法论支撑。
