# E4-A vs E3-C / E0：配对比较

> **2026-08-07 分类更正**：本文档 §2-3 原基于修复前的语义分类器（只检查聚合/排序关键词是否出现，不比较 GROUP BY/ORDER BY 具体字段和 JOIN key）。用修复后的分类器（`docs/analysis/README.md` §4.1）重新统计后，§3 的"聚合/排序 -4、Schema/Join +1"方向是反的，实际是"聚合/排序 +4、Schema/Join -4"；§2 的稳定失败同类占比也显著改变（Schema→Schema 从 12 升到 35，聚合→聚合 从 37 降到 23）。§1、§4-7 的正确率、recovered/regressed 题数、成本比较不受影响（这些由 correct/incorrect 原始判定决定，与分类器无关）。拒绝 E4-A 的最终决策不变，但拒绝理由应以本次更正为准：**E4-A 让自己的目标类别（聚合/排序）变差，而不是目标改善、被 Schema 拖累**。

## 2. E3-C → E4-A 配对迁移

```text
E3-C correct 77 ── 68 保持正确
               └─ 9 回退

E3-C failed 120 ─ 3 恢复
                └ 117 仍失败
```

同类稳定失败占主要部分（2026-08-07 修复后重新统计）：117 题仍同时失败，其中 90 题（77%）在 E3-C 和 E4-A 里的主要语义类别相同——Schema→Schema 35、聚合→聚合 23、输出→输出 22、过滤→过滤 10；另外 27 题（23%）在两次运行间改变了主要语义类别（这反映的是模型在两次运行里生成的 SQL 结构本身不同，不是分类器噪声）。QueryPlan 仍然没有改变大多数稳定错误的语义类别，但 Schema 类稳定失败的占比（35/117=29.9%）远高于原报告的 12/96=12.5%，说明 Schema/Join 才是横跨 E3-C 和 E4-A 都没解决的最大稳定问题，而不是聚合。

恢复 3 题：`bird_1472`、`bird_371`、`bird_83`。回退 9 题：`bird_1480`、`bird_1500`、`bird_1526`、`bird_1350`、`bird_1464`、`bird_989`、`bird_565`、`bird_459`、`bird_46`（题目 ID 本身不受分类修复影响，只是各自的失败归因标签变了，参见 [`e4_a_core197_run1_summary.md`](e4_a_core197_run1_summary.md) §3.2）。

## 3. 失败类别变化（2026-08-07 已用修复后分类器更新）

| 类别 | E3-C（修复后） | E4-A（修复后） | 变化 | 原报告（供对照） |
|---|---:|---:|---:|---|
| Schema/Join | 46 | 42 | **-4（改善）** | 原：15→16，+1 |
| 聚合/排序 | 29 | 33 | **+4（变差）** | 原：45→41，-4 |
| 输出契约 | 28 | 29 | +1 | 原：28→29，+1（不变） |
| 过滤/低置信度 | 15 | 17 | +2 | 原：30→35，+5（原数值偏大） |

原报告"聚合下降是真实的局部信号"这一判断不成立：聚合/排序实际是唯一净上升（变差）的目标类别，Schema/Join 才是唯一净下降（改善）的类别，两者方向与原报告正好相反。目标恢复 3、目标回退 5（见 §1 及 [`e4_a_core197_run1_summary.md`](e4_a_core197_run1_summary.md) §3.2），而不是原报告的"同为 3"；错误确实迁移到了过滤（+2，非原报告的+5）、运行失败（不变），但没有迁移到 Schema——Schema 反而改善了。

## 4. E0 稳定集合比较

| 指标 | E3-C | E4-A |
|---|---:|---:|
| E0 稳定失败恢复 | 10/124 | 9/124 |
| E0 稳定正确回退 | 0/62 | 5/62 |

E4-A 破坏了 E3-C 最有价值的性质之一：保留全部 62 个 E0 稳定正确题。5 个稳定正确回退中有 3 个输出契约、1 个过滤、1 个 MaxIterations。

## 5. QueryPlan 为什么没有转化为准确率

```text
Question + Offline Schema + few-shot
  ↓
初始 QueryPlan
  ├─ 结构无效：19 题需要修正，增加协议成本
  └─ 结构有效但语义可能错误
       ↓
SQL adherence
  ├─ 全部通过且正确：64 题
  ├─ 全部通过但失败：82 题  ← 主要问题
  ├─ 至少一次失败但最终正确：7 题
  └─ 至少一次失败且最终失败：37 题
       ↓
Observation / revision
  └─ 0 次 wrong → correct 恢复
       ↓
FINAL
  ├─ 4 题 MaxIterations 无 FINAL
  └─ 3 个曾正确轨迹最终仍失败
```

当前 adherence 是计划内部一致性检查，不是问题—计划语义正确性检查。加入更多自由文本字段只让错误决定变得更结构化，并没有提供新的可靠证据来纠正它。

## 6. 成本比较

E4-A 相对 E3-C：LLM calls `-6.13%`、延迟 `-19.65%`，但 prompt tokens `+36.52%`、total tokens `+6.67%`。由于准确率下降，不能宣称成本收益。

## 7. 决策

- 接受：E4-A 的结构化 trace 让首错定位更清楚，个别聚合/输出题得到恢复。
- 拒绝：当前 QueryPlan + Output Contract 作为准确率机制。
- 回退：正式父配置恢复为 E3-C。
- 暂停：E5/E6，不在失败的 E4-A 上继续叠加 context store 或 Leaf。
