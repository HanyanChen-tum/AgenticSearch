# DB-RLM 实验汇总报告（2026-08-11）

数据集 BIRD mini-dev 500 题（11 个数据库），模型 `azure/seminar-gpt-5.4-mini`，
`temperature=0`、`reasoning_effort=high`、`max_iterations=8`、train-only few-shot `k=1`。
**全部数字统一为官方 BIRD 集合比较口径**（`shared/evaluator.is_correct`）。

---

## 一、主结果

| 配置 | 准确率 | 说明 |
|---|---:|---|
| Baseline 2 关键词表过滤 | 51.60% | 朴素剪枝反而有害 |
| **Baseline 1 单轮 schema→SQL** | **55.20%** | 无工具、无循环，**对比基准** |
| clean-e0 纯协议提示 | 61.40% | ReAct + 活库工具，提示词仅含协议 |
| DB-RLM v4 | 64.20% | legacy 时代中期 |
| e3-c-conv | 64.60% | + Offline Schema Context + 约定后处理 |
| **e3-c-conv-rules（当前最优）** | **67.40%** | **+ train 审计过的书写规则** |
| legacy-e0 | 67.80% | legacy 提示词 + db_hints（**eval 调优**） |
| legacy 存档最好 | 69.80% | 配置已不可考 |

**相对最早基线：55.20% → 67.40%，+12.20 pp。**

当前配置的三个组件全部为 train 来源、跨库验证、可审计；legacy 的 67.80% 依赖看着测试集手写的提示词，不可作为研究结论。

## 二、有效机制（三个）

### 1. Offline Schema Context（E3-C）　+3.20 pp

将逐题注入的全量 schema 替换为**按题确定性检索**的相关片段（表/字段描述、PK/FK 图、join 的 cardinality 与 fan-out、值格式），未选中的表只给 names-only 索引。

- 对抗子集 197 题：+4.82 pp；全 500 题：+3.20 pp
- 表召回率 98.4%（492/500），漏表的 8 题准确率反而更高
- 代价：token/题 +14.29%

### 2. 标注约定后处理　+6 题（全 500）

从 train pool（9428 条、69 库）挖掘书写约定，由 harness **确定性改写**最终 SQL：

| 约定 | train 支持度 | 适用 | 多数遵守的库 |
|---|---:|---:|---:|
| 分列而非 `\|\|` 拼接 | 99.99% | 9428 | 69/69 |
| 最值用 `ORDER BY...LIMIT` | 90.34% | 1542 | 63/65 |
| 计数遇 JOIN 不去重 | 89.10% | 2377 | 65/67 |

- 197 子集 +5 题（两次独立测量一致），全 500 +6 题
- 触发 49 题，转正 11、打坏 5

### 3. train 审计过的提示词规则　+2.80 pp

legacy 提示词值 +6.40 pp 但标注为 `legacy-eval-tuned-unaudited`。逐条拿 train 验证后，**采纳 2 条、剔除 2 条**：

| 规则 | train 支持度 | 采纳 |
|---|---:|:--:|
| 最值用 `ORDER BY...LIMIT`，不用 `= (SELECT MAX)` | 90.3%（n=1542） | ✅ |
| 单问句只投影一列 | 84.5%（n=8693） | ✅ |
| 是非题返回 YES/NO 字面量 | **41.0%**（n=39） | ❌ train 反对 |
| 多问句投影多列 | **28.6%**（n=595） | ❌ train 反对 |

机制验证（不经过评分）：最值写错 **19 → 4**，单问句多投影 **81 → 70**。

## 三、泛化性验证

train pool 的 69 个数据库与 dev 的 11 个数据库**完全不相交**，因此在 dev 上的测量是留出集检验：

| 规则 | train（69 库） | dev（11 个未见库） | 迁移差 |
|---|---:|---:|---:|
| 最值用 `ORDER BY...LIMIT` | 90.3% | 92.0% | +1.7% |
| 单问句只投影一列 | 84.5% | 82.0% | −2.4% |

dev 逐库：8/8 与 11/11 个库多数遵守。

**边界**：以上仅证明**跨数据库**泛化（BIRD 内部）。这些是 BIRD 标注者的书写习惯，**跨数据集（Spider、真实业务库）未验证且很可能不成立**。因此这部分收益应报告为「标注对齐」，不得计为 Text-to-SQL 能力提升。

## 四、负面结论

### 1. 验证类干预全部失败（5 次）

E1 strict verified-final、E4-A QueryPlan、字面量核实提醒、JOIN 精简提示，加上本轮的 E6 反馈重投。
根因：失败题的 wrong→correct 恢复次数**三次运行精确为 0**，99% 以上的失败题全程从未执行出匹配 gold 的结果。

**重要限定**：这不等于「ReAct 无用」。`findings.md` 记 ReAct loop + live DB tools 为 **+9.0**。
区分在时序——**承诺之前的落地取证有效，答案已有之后的挽救无效**。

### 2. RLM 递归：五轮迭代，委派题上净收益恒为 0

| 版本 | 改动 | leaf 查库率 | 调用题净收益 |
|---|---|---:|---:|
| v1 | 纯文本 leaf | — | 0 |
| v2 | leaf 可查库 | 0% | 0 |
| v3 | 强制查库 | 0% | −2 |
| v4 | 给 leaf schema | 23% | 0 |
| v5 | 给确切代码示例 | **94%** | **0** |

v5 中 leaf 确实查库并答对（`"Business"`、`"Closed"`、`"2019-09-12"` 均为真实查询结果），机制端到端跑通，**净收益仍为 0**。

**结构性原因**：parent 自身即有 `db.execute`，leaf 查到的 parent 本就查得到——**委派未创造新信息**。
与 E5-A 同构（上下文利用率仅约 4%，外部化针对的约束不存在）：递归的两个经典理由在本任务上均不成立。

**关键发现**：项目此前所有「RLM 能力」实验测的都不是递归本身——递归原语一直在 REPL 里，但**没有任何提示词提到过它**，实测 0/197 次调用。

### 3. 静态 query patterns 与 Query Mining

- E3-A 静态 patterns 与 E3-C 组合后为 70/197，低于 E3-C 单独的 77/197，但该差距在方差内，只能说「未带来假设中的增益」
- Query Mining v2：28 个 slot 全部未通过跨库门禁，最佳 slot 仅比模型自身判断强 1.5 pp

## 五、基准质量发现

对当前最优配置在 197 对抗子集上的 **115 题失败逐题审计**（全量普查，非抽样）：

| 根因 | 题数 | 占比 |
|---|---:|---:|
| gold 本身有缺陷 | 44 | 38.3% |
| 输出约定未指定 | 22 | 19.1% |
| 指代歧义 | 18 | 15.7% |
| Hint 与 gold 自相矛盾 | 14 | 12.2% |
| 标注约定残留 | 7 | 6.1% |
| **模型真实推理错误** | **10** | **8.7%** |

系统性 gold 缺陷模式：AND/OR 优先级 bug、条件恒真、经 postHistory 连接放大计数、gold 自身超时或返回 None。

**含义**：该对抗子集已不适合评估能力型机制——91% 的失败不是能力问题。

## 六、方法论

### 同配置重跑方差 = 6 题（3 pp）

同超参两次运行：77/197 与 71/197，逐题翻转 10 题，**SQL 逐字相同仅 10.7%**。
`temperature=0` 不锁定输出，因约 93% 的 completion token 是每次不同的隐藏推理。

**由此收回一个结论**：e3-ac 低 7 题曾被判为「静态 patterns 有害」，−7 只比噪声大 1 题，不成立。
显著性阈值从 2 pp 上调至 3 pp。

### 「含糊 vs 确切」措辞（本轮新发现）

两次独立验证：

| | 含糊 | 确切 | 效果 |
|---|---|---|---|
| 约定规则 | `consider whether DISTINCT is required` | `Do not write WHERE col = (SELECT MAX...)` | 违反 19→4 |
| leaf 查库 | `you may use db.execute` | 直接给出可照抄的代码块 | 0% → 94% |

而历史上四个失败的 Prompt 机制**全部为含糊措辞**。它们可能不是机制无效，而是措辞无效——**该假设未经检验**。

### 实验纪律（由本轮两次未遂错误结论固化）

1. 凭证经 `resolve_llm_config`、路径经 runner 常量，不自行推导——曾因直接读环境变量导致 10 题全 `APIError` 被记为「递归无效」；曾因自推数据库路径使后处理看似 −3
2. **异常不得吞为结果值**，基础设施失败单独记账
3. **触发集实验至少重复 3 次**——曾有单次运行显示恢复，三次重复证明只在 1/3 中出现
4. **优先采用不经过评分的指标**（违反计数、查库率、调用率），它们不受运行方差影响
